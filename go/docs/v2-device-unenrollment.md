# UUID device unenrollment

Implements [WDY-3313 — Cloud v2 device enrollment leaves Jetson unprovisioned after reserving an asset](https://linear.app/wendylabsinc/issue/WDY-3313/cloud-v2-device-enrollment-leaves-jetson-unprovisioned-after-reserving) and [WDY-3534 — Preserve deleted Cloud asset bindings for stateless unenrollment recovery](https://linear.app/wendylabsinc/issue/WDY-3534/preserve-deleted-cloud-asset-bindings-for-stateless-unenrollment).

> **Contract scope:** AAA v0.22 (retained in v0.24), §5.1/§7(4), explicitly excludes removal-only unenrollment—asset deletion, device-certificate revocation and device reset—from step-up. No fresh FIDO2/passkey interaction is required. Intent confirmation is not authentication: exact `device:delete`, an exact-body operator-signed request, retained deletion evidence, audit and SSF remain required. This is the WDY-3585 amendment, not a temporary security workaround.
>
> **Applicability:** AAA governs Cloud/Auth/PKI and their request validation. The CLI implements the affected Cloud interface: exact binding, authorization and operator-signed requests. Local guarded erasure and recovery do not inherit backend postbox duties; this operation does not introduce a queued device-command path.
>
> **Rollout status:** This describes source behavior, not deployed acceptance. Compatible Cloud and Agent builds are required; no deployment or live-reset readiness is claimed.

## One business operation

Cloud owns unenrollment for CLI and console callers. Its signed DeleteAsset path checks device:delete, relays PKI RevokeByPrincipal, then atomically removes the active asset and records the deletion audit. A relay failure retains the active asset; revocation already completed before an audit/database failure is irreversible and retry finishes deletion. The CLI and Agent do not perform a second ACME revocation. The old prerelease RevokeACMECertificate and CheckACMERevocation RPCs return Unimplemented.

`wendy device unenroll --force` clears an enrollment left on a LAN device that Cloud has no record of. That local reset is a separate, explicitly requested operation with no Cloud deletion or revocation claim.

The CLI signs the Cloud request and its exact tenant/device revoke_principal management authority with the same operator leaf. Existing kid/x5c behavior is retained, with a fresh PKI replay identity on each retry. Numeric Cloud v1 reads the complete certificate inventory, revokes it and deletes the asset first, and resets the device only after Cloud confirmed the deletion; authorization is Cloud's, so a refusal leaves the device untouched. This does not add a numeric fallback for PKI identities.

## Preconditions and phases

1. Read Agent provisioning through direct verified LAN mTLS. Require exact tenant/operator scope and installed peer principal/fingerprint; reject proxy/plaintext for an active device. Match the enrolled Cloud endpoint. The Cloud flow requires CloudAuthenticatedResetSupported before mutation or `--check`; `--force` requires LocalResetSupported instead. The prerelease CloudUnenrollmentSupported flag is ignored, and current Agents report it false so prerelease CLIs stop before Cloud mutation.
2. Read GetAsset using organization_id + device_id and the exact asset UUID when supplied. Active returns Asset; validate all three binding fields. After deletion Cloud intentionally returns plain NotFound. This permits only an explicit --asset-id retry, never a deletion or completion claim by itself.
3. Invoke signed Cloud DeleteAsset with expected_device_id and reset_certificate_sha256 for the exact installed leaf. This requests signing capability before a new deletion; an exact-asset retry obtains fresh authorization from the original deletion audit. Authenticate reset_authorization against Cloud HTTPS keys and the actual operator, then retain its exact embedded deletion bytes. No GetAsset tombstone is expected. Lost responses mean unconfirmed progress, not rollback.
4. Retrieve issuer-signed OCSP revocation evidence for the exact installed leaf. Request a SHA-256 CertID: Wendy PKI pre-signs this form and rejects the library-default SHA-1 request. Fetches dial only checked public IP addresses, do not follow redirects or use environment proxies, and retain standard HTTP/HTTPS OCSP with issuer signatures as authority. This is verification, not revocation. Reject good/unknown, stale/future, forged or mismatched issuer/serial evidence; preserve keys on failure. Issuer signatures support native ML-DSA as well as existing certificate algorithms; no signature verification is skipped.
5. Obtain a fresh Cloud-signed authorization by replaying DeleteAsset with expected_device_id and reset_certificate_sha256 for the exact installed leaf. Current membership, device:delete and lifecycle ACLs apply again; original deletion actor/time remain immutable. Cloud returns reset_authorization only after committed deletion and durable asset.reset.authorized accounting. Success alone is not reset authority.
6. Send existing Agent Unprovision with principal/fingerprint, PKI evidence, exact serialized deletion binding and cloud_reset_authorization. Agent independently fetches ML-DSA-65 keys over verified HTTPS from the SAVED enrollment Cloud's `/.well-known/wendy-cloud-grants/jwks.json`, never a caller key/URL. TLS certificate validity is checked throughout authenticated time; redirects and environment proxies are disabled. The compact JWS requires typ asset-reset-authorization+jws, aud wendy-agent/unprovision, exact issuer, ≤30-second lifetime and canonical replay identity. Agent also verifies the embedded operator's exact-body request signature against the actual mTLS peer leaf, including request digest, tenant/asset/device/fingerprint, method, nonce, correlation and expiry. Typed deletion fields, OCSP or operator mTLS alone cannot authenticate Cloud's decision. Operator-certificate validity and revocation-evidence freshness must hold throughout a fresh authenticated Roughtime interval; failed or unavailable time checks retain credentials.

`--check` reads Cloud binding and Agent capability only; with `--force` it checks the forced local reset path instead. It does not revoke, spend EAB, reset, import proof or write a CLI journal. All v2 phases have a three-minute command bound. A false progress flag means unconfirmed, not reversal of a remote mutation.

## Forced local reset when Cloud has no asset

Cloud returns the same plain NotFound to a caller who is not a member of the tenant or whose device access entries do not reach the device (`requireAssetMembership`, `requireDeviceAccess`). NotFound therefore never selects local reset by itself: the operator must pass `--force`, which cannot be combined with `--asset-id` or `--cloud-only`. The CLI still performs the authenticated GetAsset lookup first. An active asset refuses `--force` and keeps the Cloud flow; authorization failures, network failures and other statuses stop the command. Only NotFound proceeds. A NotFound returned by a later Cloud deletion or proof request cannot trigger local reset. Without `--force`, NotFound keeps the error that asks for `--asset-id` and now also mentions `--force`.

The CLI requires direct verified LAN mTLS, an operator certificate in the installed device's tenant, the exact installed principal and certificate fingerprint, and the Agent's `local_reset_supported` capability. The confirmation prompt describes local credential erasure and warns that NotFound can also mean the account cannot access the device; `--yes` accepts it and is required with `--json`. The Agent independently requires operator mTLS from the same tenant and checks the exact installed identity before accepting the local reset request; plaintext or a caller-supplied identity cannot authorize it. The CLI also refuses a Cloud tunnel or session proxy, but the Agent does not distinguish the transport. Before erasing anything, the Agent re-reads its saved pending record through the same protected-storage check startup recovery uses, and restores the enrolled state if that check would refuse it.

Local reset clears enrollment credentials and saved Cloud connection state. It does not request Cloud deletion, PKI revocation or a Cloud-signed reset authorization, and emits no Cloud completion receipt. Output reports local cleanup only. A bare NotFound remains insufficient to prove that Cloud deleted an asset or revoked a certificate.

Before deleting any credential, the Agent durably saves a distinct local pending state in the protected provisioning state. Startup resumes pending local cleanup before loading or serving enrollment. This state cannot satisfy the Cloud receipt verifier, and interrupted Cloud-proof recovery cannot be reinterpreted as a local reset. Cleanup failures retain pending state for retry. Completion leaves the device unprovisioned without a Cloud completion receipt; an identity-free completed marker lets startup reclaim dependent resources exactly as it does after a Cloud receipt. Both resets share the Agent's post-erasure resource cleanup and restart.

Open: the Agent authorizes `local_only` for any same-tenant operator certificate. It cannot see Cloud roles or device access entries, so `--force` guards against an accidental wipe by an honest operator, not a modified client. Gating it on organization-level device:delete and recording it in Cloud needs a Cloud-signed authorization the Agent verifies, like DeleteAsset's reset authorization; that is pending AAA review.

This path needs an updated CLI and Go Agent. Older Agents that omit the capability refuse `--force`. The Swift Agent remains unsupported. Numeric v1 and Wendy Lite retain their existing cleanup paths.

## Re-entry without CLI workflow state

There is no CLI journal, saved phase or reusable enrollment credential. For the Cloud flow, the short-lived purpose-specific authorization travels directly through the existing CLI→Agent path. Historical unenroll/unenroll-v2 journals remain untouched and are not authority. The receipt recovery below applies to the Cloud flow; local pending recovery uses the distinct state described above.

- Active asset: retry the same Cloud operation; already-revoked principal credentials are a no-op.
- Cloud deletion with device still provisioned: supply the original --asset-id, obtain fresh signed audit evidence and PKI revocation proof, then retry guarded erasure.
- Erasure interrupted: before deleting any key, Agent atomically saves and syncs the verified Cloud proof, its HTTPS-authenticated verification key, operator certificate and public device-signed pending reset authorization in the existing `provisioning.json` under `unenrollment` (`status: pending`, `receipt`). That file survives credential cleanup. Startup verifies the receipt and exact saved enrollment binding and resumes bounded cleanup before loading or serving enrollment. Incomplete recovery fails closed and blocks new enrollment.
- Reset completed but reply lost: after key removal and directory sync, Agent atomically replaces `provisioning.json` with minimal unprovisioned state containing only `unenrollment` (`status: completed`, `receipt`), then syncs the file and directory. No additional persistent recovery files are created. Agent publishes the signed completion receipt only from completed state. Its existing IsProvisioned response carries that public receipt. A fresh CLI validates the old certificate's signature and configured trust roots, re-establishes Cloud signature-key trust from current HTTPS JWKS, checks PKI/Cloud evidence at the saved authorization time, and reads the current tenant/device binding to refuse a re-enrollment. Only a version-2 receipt with independently authenticated Cloud authority can support confirmation; plain NotFound alone is never proof. A remote device-supplied verification key is never independently trusted. It reports completion of that **prior principal's operation**, not a newly authenticated current device identity. Plaintext transport/mDNS are not identity proof and carry no mutation authority.
- Re-enrollment: after a completed reset the Agent holds no device key, ACME account key, relay state or Cloud/asset binding beyond that public receipt, and ACME enrollment replaces it. Per sem's 2026-10-15 12:56 ruling, an authenticated unenroll removes the device from records: it may re-enroll with the same device ID in the same or a different organization. Cloud keeps only a non-blocking, invisible deletion audit record for proof replay and compliance; that record never appears as an asset and never blocks enrollment (Cloud #754).

`ReadCompletion` verifies the receipt's signatures and internal binding; it is not a trust-root or current-peer verifier. The CLI separately anchors the historical certificate to its configured roots before trusting remote public evidence. Agent recovery reads only its root-owned 0600 state, originally written after installed-leaf/operator verification; pending evidence is re-bound to that stored identity. New reset authorization queries the existing baked-in Roughtime servers for fresh nonce-bound signed evidence under a five-second deadline. At least two independent agreeing responses are required, using the existing verified/degraded consensus policy. Operator validity and issuer-signed OCSP freshness must hold across the entire returned interval; deletion must precede its lower bound and the receipt records its upper bound. Time acquisition releases the provisioning lock; caller and exact installed identity are rechecked afterwards. Monotonic elapsed time accounts for waiting to reacquire the lock. No cached consensus, boot hint or system wall-clock reading is erasure authority. The reset query does not change the system clock or read/write a clock floor; primary OS/Agent time persistence remains separate. If fresh signed time is unavailable, local credentials remain for retry even after Cloud deletion/revocation succeeds. Restart recovery verifies the saved receipt at its recorded authorization time and resumes the already-authorized cleanup without a new time query.

V2 receipts preserve the exact nanosecond authenticated admission time as well as its legacy seconds field. They contain only public certificate/chain, principal, Cloud endpoint, asset UUID, installed fingerprint, authorization time, PKI-signed status, typed deletion binding, Cloud authorization/verified public key, public operator certificate and device signature. Historical proof-less pending receipts remain blocked without erasure; already-completed historical receipts remain readable. Protected LOCAL pending recovery trusts its originally authenticated saved key and needs no network. REMOTE v2 confirmation fails closed if a retired historical signing key is no longer published by Cloud; indefinite public key-history support is not asserted. No private key, ACME account key, EAB secret, bearer token or operator key is written to it. Historical development proof files are ignored and preserved. Normal enrollment replaces the existing provisioning state, dropping its prior completion receipt. Historical development files remain ignored and untouched; there is no importer for separate pending/completion files. Downgrading to an Agent that ignores pending recovery is unsafe until the authorized reset has completed.

## Rollout and limits

Flashing is an explicit local reset, not an unenrollment transaction. Valid first-boot provisioning may replace previous pending/completed recovery state. An ordinary restart still verifies and resumes pending reset recovery. Flashing does not implicitly revoke certificates or delete Cloud records; the operator must clean up the old Cloud identity separately. No automatic Cloud-cleanup prompt or workflow is introduced here.

The historical GetAsset deletion-detail contract is no longer consumed. The signed-proof contract [service-protos #115 — Document Cloud-owned unenrollment signing and phases](https://github.com/wendylabsinc/service-protos/pull/115), compatible [Cloud #754 — Cloud-owned unenrollment](https://github.com/wendylabsinc/cloud/pull/754) (including Sem's fixes), and an updated Agent are required before using this consumer. Unreleased development servers/agents are not a compatibility promise. Migration numbers and cumulative landing order must be reconciled before main deployment; source maximum is not a live migration cursor.

Cloud-only unenrollment can finish without a reachable device, but cannot erase an offline device's local credentials. Missing or purged Cloud evidence cannot prove Cloud deletion or revocation; an authenticated bare NotFound permits only the explicitly forced LAN local reset described above. Missing or unavailable OCSP evidence preserves local keys in the Cloud flow even after Cloud completes. A receipt proves the earlier operation, not current physical-device identity or reachability. No live acceptance, installation or deployment is implied by source tests; the earlier production user-run acceptance used a different build.
