Wendy Cloud connects your CLI to devices outside your local network. Enrolled
devices connect outbound, so you do not need to open inbound ports or assign
public IP addresses. You can still build and operate local devices without a
Cloud account.

Use **Cloud v2** for new setups. Choose **Legacy** if your devices still belong
to Cloud v1. Signing into v2 does not move existing devices or applications.
Follow [Moving to Cloud v2](/docs/cloud-migration) before migrating a deployment.

## Start with Cloud v2

These examples use CLI [2026.10.17-123916](https://github.com/wendylabsinc/WendyOS/releases/tag/2026.10.17-123916)
or newer. You need the [current Wendy CLI](https://github.com/wendylabsinc/WendyOS/releases),
access to your organization in [Wendy Cloud](https://cloud.wendy.dev/login), and
a supported device running a compatible Wendy Agent. Keep local access to the
device during its first enrollment. Use an owner or admin account to enroll it;
access to other operations depends on your organization's permissions.

### Sign in and check your organization

```sh
wendy cloud login
wendy cloud status
```

The current CLI opens the production Cloud v2 sign-in page. Select your
organization in the browser. The CLI saves a named context containing your
Cloud session and operator certificate. An older CLI may default to Cloud v1;
update it before following this guide.

If you have multiple saved contexts, sign-in can leave the previous context
active. Use `wendy cloud status` to inspect their names and endpoints, then
select the intended one:

```sh
wendy auth use <context-name>
```

For v2, check that the selected context points to `cloud.wendy.dev` and reports
an OIDC login. [Login options](/docs/advanced/clients/wendy-cli/commands/cloud/login)
cover email-based sign-in and service accounts.

### Enroll a new device

Connect the device locally by USB networking or LAN, discover it, and enroll it
using the selector returned by discovery:

```sh
wendy discover
wendy device enroll --device <local-device-selector> --name shop-floor-01
wendy cloud discover --all
```

`wendy cloud enroll-device` is an alias for `wendy device enroll`. The device
receives its own identity and Cloud binding. Wait for it to appear
online before trying remote commands. A successful sign-in alone does not
enroll a device. For an already enrolled v1 device, use the
[migration guide](/docs/cloud-migration) instead of repeating enrollment.

Wendy Lite has a separate firmware workflow and requires physical USB access
for enrollment. Start with [ESP32 setup](/docs/installation/wendy-lite-esp32).
Mac targets also have their own [setup and limitations](/docs/installation/wendy-agent-macos).

### Discover, deploy, and verify

```sh
wendy cloud discover
wendy cloud discover --all
wendy cloud discover --json
```

Discovery shows online devices by default. `--all` includes offline devices;
`--json` supports scripts. Cloud v2 identifies devices with UUIDs. Use a name
or UUID returned by discovery, rather than a legacy numeric asset ID.

Pick the device in the **Cloud** tab of the device picker, or name it with
`--device`. The `selector` that `wendy cloud discover --json` prints for each
device keeps its Cloud endpoint, organization, and device identity, so renaming
the device or switching context does not retarget it.
From your app's project directory:

```sh
wendy run
wendy cloud device apps list --device shop-floor-01
wendy cloud device logs --device shop-floor-01
```

The saved Cloud target makes `wendy run` deploy through Cloud. Check the app's
state, logs, and expected output after deployment. A completed upload does not
prove the application is ready. To reach an app's own web or API port
remotely, use a tunnel as described below.

### Reach services through a tunnel

Cloud v2 forwards TCP or UDP to any port from 1 through 65535 on the device's
loopback interface. Arbitrary ports need an updated Cloud service and CLI and
Wendy Agent [2026.10.22-211023](https://github.com/wendylabsinc/WendyOS/releases/tag/2026.10.22-211023)
or newer. Older v2 versions forward only TCP port **50052** for Wendy Agent and
TCP port **22** for SSH.

```sh
# An HTTP service listening on device port 3000
wendy cloud tunnel 8080:3000 --device shop-floor-01

# A UDP service listening on device port 9000
wendy cloud tunnel 9000:9000/udp --device shop-floor-01

# The Wendy Agent service
wendy cloud tunnel 15052:50052 --device shop-floor-01
```

The Agent port is a transport for an authenticated client, not a web page.
Forwarding it does not remove the Agent's authentication requirements. Keep the
command running while using a tunnel, then press Ctrl+C to close it.

<Callout type="warn">
  A tunnel reaches only a service that is already listening on the device. Port
  22 works only when the target actually runs SSH; release Jetson and Raspberry
  Pi images do not include an SSH server.
</Callout>

Cloud selects the v2 relay. Do not pass `--broker-url` for a v2 session.
See the [tunnel reference](/docs/advanced/cloud/tunnel) for UDP limits,
selection rules, and errors.

### Use service accounts for automation

A tenant admin can create a service account and enroll its key. Then sign in
without an interactive browser:

```sh
wendy cloud login --service-account ./wendy-service-account.json
```

Follow [service-account setup](/docs/advanced/clients/wendy-cli/commands/auth/login#service-account-login)
to create the key and configure CI. Service-account login does not issue an
operator certificate. Successful sign-in does not imply that device deployment,
compute-device tunnels, or certificate-signed operations are available to that
account. Check the operation's permissions and supported principal type before
moving an unattended collector or deployment pipeline to v2.

## Keep using Cloud v1

Use this path for devices that are still enrolled in
[legacy Wendy Cloud](https://cloud.wendy.sh). The current CLI retains the v1
login flow behind an explicit flag:

```sh
wendy cloud login --legacy
wendy cloud status
```

If another saved context is active, select the legacy context by the name shown
in `status`:

```sh
wendy auth use <legacy-context-name>
wendy cloud discover --all
```

Check that its dashboard is `cloud.wendy.sh` and its login path is legacy.
`wendy auth login --legacy` is an equivalent entry point. Signing into v2
does not replace the credentials installed on your v1 devices.

### Operate existing devices

```sh
wendy cloud device apps list --device shop-floor-01
wendy cloud device logs --device shop-floor-01
```

Legacy discovery supports numeric asset IDs as well as device names. Keep
existing scripts on their matching legacy context until you have validated the
v2 replacements. To deploy, run `wendy run` from your project and select the
device in the picker's **Cloud** tab.

### Forward an application port or UDP service

Legacy sessions keep their existing TCP and UDP forwarding. Each example needs
a service already running on the remote device.

```sh
# An existing HTTP service listening on device port 80
wendy cloud tunnel 8080:80 --device shop-floor-01

# An existing UDP service listening on device port 9000
wendy cloud tunnel 9000:9000/udp --device shop-floor-01
```

For a complete UDP example, use
[Reach a UDP service through Wendy Cloud](/docs/guides/tutorials/python/cloud-udp-service).
Keep the tunnel running while using the service.

### Plan your upgrade

Check application ports and UDP, unattended access, notification delivery, and
Companion support before changing device enrollment. On v2, application ports
and UDP need the updated Cloud, CLI, and Agent versions. Use
[Moving to Cloud v2](/docs/cloud-migration) to validate a spare device and plan
the cutover. Keep the working v1 deployment until its replacement is verified.

## Connect Cloud to the rest of Wendy

| What you want to do | Start here | What to check |
| --- | --- | --- |
| Alert operators in Companion | [Send notifications from an app](/docs/guides/device-notifications) | App registration, assignment, notification entitlement, Cloud grant, and a compatible signed-in Companion build. Push delivery is best-effort. |
| Record sensor data or model results | [Wendy Data](/docs/data) | Recordings can stay local. Cloud enrollment alone does not configure upload, retention, or a BI connection. |
| Analyze operating data | [Wendy BI](https://wendy.dev/products/wendy-bi) | BI has its own access and data-connection setup. Confirm the supported source and integration with the Wendy team. |
| Work through an AI assistant | [MCP setup](/docs/guides/llm-integration) and [ChatGPT setup](/docs/guides/chatgpt) | Local tools and hosted access have different setup requirements. Device permissions still apply. |

For a product map, see [The Wendy ecosystem](/docs/concepts/ecosystem).
For device identities, permissions, and unfinished security controls, see
[Security](/docs/security). The [Cloud reference](/docs/advanced/cloud/requirements)
contains protocol requirements; requirements are not a guarantee that every
workflow is available in the deployed service.
