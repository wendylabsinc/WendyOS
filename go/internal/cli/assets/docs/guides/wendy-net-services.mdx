---
title: Share and discover app services
description: Publish TCP or UDP services across Wendy Net using mDNS, with an app-owned discovery socket or private Avahi.
---

Let an app on one Wendy device find and connect to an app on another. Your app
advertises a service using normal mDNS/DNS-SD, the discovery protocol used by
Bonjour and Avahi. Wendy Net carries admitted service information between devices;
apps browse it through their own network interface.

To connect by hostname without browsing, see
[Connect to a known device](#connect-to-a-known-device).

Start by [connecting the devices](/docs/guides/wendy-net) and checking their peers.
Use current Linux WendyOS images with full Wendy Net support.

Run these commands in an interactive terminal. Select the intended device when prompted, or check the target `WENDY_DEVICE` selects automatically.

## 1. Give the publishing app Wendy Net access

Merge this into its `wendy.json`:

```json
{
  "appId": "com.example.net-api",
  "platform": "linux",
  "version": "1.0.0",
  "isolation": "isolated",
  "entitlements": [
    {
      "type": "network",
      "mode": "mesh",
      "serviceCIDR": "10.99.0.0/16",
      "ports": [
        { "host": 18080, "container": 8080, "protocol": "tcp" }
      ]
    }
  ]
}
```

Keep the literal configuration value `"mesh"`; it selects Wendy Net service
networking. Use `10.99.0.0/16`, the currently supported service address range.
`serviceCIDR` is the virtual address block for mesh services. `/16` fixes the
first 16 bits, so this block spans `10.99.0.0` through `10.99.255.255`.
It is not a single server address and does not change the LAN or container IP.
Use the supported range on both apps; connect to the address returned by discovery,
not an address invented within the range.

Run your server on the container's address or `0.0.0.0:8080`, not loopback alone.
The example publishes TCP port 18080 for other Wendy Net apps. Choose an unused
published port if another app on the same device already uses it.

For UDP, set `"protocol": "udp"` and advertise a type ending in `._udp`.
Omitting `protocol` selects TCP. TCP and UDP mappings are separate, even when
they use the same port number.

Deploy after saving:

```sh
wendy run
```

The port mapping permits incoming connections; it does not announce a service
by itself. The app must also publish a discovery announcement as described below.

## 2. Publish with your app's mDNS library

If your app already uses a library that opens its own mDNS socket, keep using it.
It needs no `avahi`, Bluetooth, or direct Wi-Fi Aware entitlement.

For the example above, advertise:

| Value | Example |
| --- | --- |
| Instance name | `My API` |
| Service type | `_http._tcp.local.` |
| Hostname | An app-owned `.local.` hostname. |
| Address | The app's IPv4 address on `eth0`. |
| Port | The **container** port, `8080`. |
| TXT data | Your service metadata, or an empty TXT record. |

Use the container interface for multicast discovery. Publish the complete PTR,
SRV, TXT and IPv4 address records; most DNS-SD libraries produce these together.
Keep them refreshed while the server is available, and send the library's goodbye
or unregister the service when stopping it. Advertising an unrelated host address
or an undeclared port does not publish an accessible Wendy Net service.

Wendy translates the announced container port into the declared published port.
Remote browsers receive a Wendy Net service address and port 18080 in this example.
Use those returned values to connect; do not substitute the publisher's container
or management address.

### Applications that put endpoints in TXT

Wendy preserves application TXT values. It does not rewrite IP addresses, URLs,
or extra service ports embedded in them. A client that prefers a TXT address
over the resolved DNS address can dial the publisher's private container subnet
instead of its Wendy Net address. Use resolved addresses for mesh connections.
Private container addresses can be identical on different devices.

If a protocol encodes extra ports in TXT, declare each required incoming port
and keep the published and container port numbers equal unless the application
can advertise the translated values. An SRV mapping does not authorize those
additional ports automatically. See the
[NVIDIA PAIR example](/docs/guides/nvidia-pair) for this pattern.

Do not add a UDP 5353 port mapping to forward multicast between devices. The
agent observes app mDNS on its private bridge and projects service records;
it does not flood raw multicast across the mesh.

## 3. Browse from a second app

Give the client a private Wendy Net network too. It can omit incoming ports if
it only makes outbound service connections:

```json
{
  "appId": "com.example.net-client",
  "platform": "linux",
  "version": "1.0.0",
  "isolation": "isolated",
  "entitlements": [
    {
      "type": "network",
      "mode": "mesh",
      "serviceCIDR": "10.99.0.0/16"
    }
  ]
}
```

Deploy to another connected device and browse `_http._tcp.local.` with the app's
mDNS library. Resolve a result and connect to its returned address and port.
Display names may gain a suffix to distinguish identical services from different
devices; avoid matching an entire generated name as a permanent identifier.

Service discovery can cross intermediate Wendy Net devices without a direct
connection to the publishing device. Discovery is not an application health
check: verify an actual request to the discovered server.

## Connect to a known device

An app can also connect to a specific enrolled device without browsing or
publishing a DNS-SD service. Enroll both devices in the same Wendy Cloud
organization. The client agent must support short device DNS. Run the
[DNS check below](#verify-short-dns-from-the-client-app) to check the installed
client directly. For offline friendly names learned through mesh, the destination
agent also needs support for publishing its Cloud-registered name to the signed
directory. See the [WendyOS release notes](https://github.com/wendylabsinc/WendyOS/releases)
for availability. Keep the client in network mode `mesh` and
[publish the server's incoming ports](#1-give-the-publishing-app-wendy-net-access).
Use the destination's certificate UUID for `<device-uuid>`. The
[inventory lookup below](#look-up-a-device-uuid) shows how to
retrieve it. Use either name with the **published** port:

```text
jetson.wendy.internal:18080
device-<device-uuid>.wendy.internal:18080
```

The friendly name is scoped to the client's enrolled organization. Device
names are registered as lowercase DNS labels of up to 63 characters. A label
starts with a letter, uses ASCII letters, digits, and hyphens, and ends with
a letter or digit. DNS queries are case-insensitive. Hyphens are preserved,
so `jetson-a` and `jetson--a` name different devices. The `device-<uuid>` form
is reserved for UUID lookups. Use it in app configuration that must survive
a device rename.

The agent checks the signed Wendy Net directory and the organization's
authenticated Cloud roster for short friendly names. Older agents publish a
local name in the signed directory. Agents with Cloud name support publish their
Cloud-registered name in the signed directory and in the optional LAN
discovery `cloud-name` TXT record after their first roster sync. They retain the
last confirmed name during an outage, including after reboot. The LAN
`name` record continues to carry the local device name, which can change
immediately on a local rename. If the device has never confirmed a Cloud
name, use its UUID or local hostname where supported. A missing, invalid, or
ambiguous Cloud label leaves the local advertisement unchanged.

One unambiguous binding from either source is enough. If both sources bind the
name, they must identify the same device.

The calling host allocates virtual IPs from the app's `serviceCIDR`, the
`10.99.0.0/16` range configured in [step 1](#1-give-the-publishing-app-wendy-net-access).
The connection still needs a usable local mesh or Cloud route, must authenticate
the exact tenant/device principal, and must pass the destination's running-app
port authorization. Keep the hostname in configuration because the virtual IP
belongs to the calling host. Follow the
[Wendy Net setup guide](/docs/guides/wendy-net) to establish a local mesh route.

For Cloud fallback, both agents need `wendy-app` support and the source
device needs a `tunnel:request` grant scoped to the destination. See the
[Cloud relay prerequisites](#connect-through-wendy-cloud).

`device-<uuid>.mesh.wendy.internal` and `device-<uuid>.cloud.wendy.dev` are
existing UUID aliases. Short DNS support adds `device-<uuid>.wendy.internal`.
When the client's resolver supports all three spellings, they share one VIP
allocation. Existing apps can keep using the two older spellings or the older
org-qualified friendly aliases.

An unenrolled client gets NXDOMAIN for both short hostname forms. An enrolled
client can get a virtual address for a well-formed UUID even when no device
has that UUID. A friendly-name lookup returns NXDOMAIN if neither the signed
directory nor the Cloud roster knows the name, or if the sources tie it to
more than one device. Use `device-<uuid>.wendy.internal` to select one device
explicitly.

### Select a device in the CLI

Use the same `*.wendy.internal` hostname with `--device` on the Wendy CLI.
First sign in through the browser with `wendy cloud login`, then select the
device's organization with `wendy auth use` if you have multiple contexts.
This obtains the operator certificate used to authenticate the CLI connection;
a service-account login does not provide it. CLI device selection does not require
a desktop VPN or an app network entitlement on your computer. See the
[CLI device selection guide](/docs/advanced/clients/wendy-cli/device-selection).

### Look up a device UUID

From a terminal signed in to the destination's Wendy Cloud organization, list
its enrolled devices, including offline devices:

```sh
wendy cloud discover --all --json
```

Find the destination by its `name` and copy the UUID in `pkiDeviceName`.
For example, a device entry can contain
`"pkiDeviceName": "00000000-0000-4000-8000-000000000001"`.
If `pkiDeviceName` is missing, use the `id` field if it contains a UUID.
For a device with only a numeric ID, use a Cloud selector in the CLI or try
the friendly-name DNS check below from an app.

### Verify short DNS from the client app

{/* Keep this heading's existing #verify-short-dns-from-the-client-app anchor.
    UUID inventory lookup has its own heading above; existing DNS links still land here. */}

First [look up the destination's UUID](#look-up-a-device-uuid) in Cloud inventory.

Confirm the enrolled client's `wendy.json` uses network mode `mesh` and
`serviceCIDR` set to `10.99.0.0/16`. Inside its app container, set
`DEVICE_UUID` to the copied UUID and run the lookup.

```sh
getent ahostsv4 "device-${DEVICE_UUID}.wendy.internal"
```

Expect an address in `10.99.0.0/16`. The resolver allocates a virtual
address for a well-formed UUID even if no device has that UUID. Verify the
device in the inventory and connect to the published port to confirm
reachability. If the lookup returns no address, check client enrollment,
network mode, and short DNS support in the [WendyOS release notes](https://github.com/wendylabsinc/WendyOS/releases).

For an offline friendly-name check, verify the destination agent's support
for Cloud-registered name publication before running the next command.
Run [`wendy device info`](/docs/advanced/clients/wendy-cli/commands/device/info)
against the destination and read **Agent Version** in the text output.
Look for short device DNS and the `cloud-name` mDNS record in the
[WendyOS release notes](https://github.com/wendylabsinc/WendyOS/releases)
at or before that version.

To check the destination's friendly name, replace `jetson` in the examples
with the target's enrolled DNS label.

```sh
getent ahostsv4 jetson.wendy.internal
```

If the friendly name returns no address, check whether the signed directory or
Cloud roster has learned that name. Conflicting bindings also prevent a
friendly-name answer. Use the UUID hostname to select the device in that case.

For an HTTP app, verify the connection on the published TCP port.

```sh
curl --fail http://jetson.wendy.internal:18080/
```

If DNS returns an address and the request fails, check the route and the
destination's published port in [Troubleshoot discovery](#troubleshoot-discovery).

### Connect through Wendy Cloud

Cloud app relay requires the source and destination apps to use network mode
`mesh` in their `wendy.json`. The destination app must publish its incoming port.
The device's [Wendy Net participation setting](/docs/guides/wendy-net#2-enable-the-connections-you-want)
controls local peer routes independently of the app's network mode. With
participation disabled, the source app can still use its `mesh` network and
virtual IP to reach Cloud.

Wendy Net tries Cloud for TCP or UDP when the source has no active local mesh
route to the destination. Local connection failures such as an identity or
published-port refusal end the attempt.

Keep both devices enrolled in the same Wendy Cloud organization. The backend
must support `wendy-app` device-originated app connections. Both the source
agent that makes the request and the destination agent that receives it must
run the WendyOS release that introduces `wendy-app` support or a later release.

Run `wendy device info` against the source device, then against the destination.
Check **Agent Version** for each device against the release that introduces
`wendy-app` in the [WendyOS release notes](https://github.com/wendylabsinc/WendyOS/releases).
Update the destination agent before updating the source. An older destination
rejects `wendy-app` connections, including requests from an updated source.

The source device needs an ML-DSA signing certificate. If the Cloud relay
error says it requires an ML-DSA device request-signing certificate, check
the source agent's enrollment and renewal logs:

- A device enrolled through pki-core renews automatically. Keep the source
  agent online with access to Wendy Cloud. It checks at startup and every
  six hours, and requests an ML-DSA-65 certificate when less than a third of
  its current certificate's lifetime remains. Retry after the agent logs
  `device_cert_renewed` and restarts. If it logs
  `device_cert_renewal_failed`, use the accompanying error to troubleshoot.
- For a device enrolled through the older Cloud issuer, arrange enrollment
  through pki-core with your Wendy Cloud administrator. If a pki-core
  device's certificate has already expired, ask the administrator for
  certificate recovery.

In Wendy Cloud, grant the **source device** `tunnel:request` permission scoped
to the **destination device's UUID**. Cloud may return `target device not found`
when it denies the grant. Check the destination's enrollment and the source's
active grant for that destination UUID.

To verify Cloud relay, use test devices that can reach Wendy Cloud and have no
local mesh route to each other. Run
[`wendy net topology`](/docs/guides/wendy-net#3-check-the-result) against the
source to confirm it has no route to the destination. Then retry the request
from the source app to the destination's published port. A successful request
in this setup verifies the Cloud path. A backend without `wendy-app` support
returns this relay error.

```text
Cloud does not offer device-originated application relays; the Cloud backend must support the wendy-app service
```

If the destination agent version is correct and the connection still fails,
check its logs for Wendy Net identity or native TLS ingress startup errors,
`Cloud application admission unavailable`, and
`Cloud application admission stopped`. These indicate problems preparing or
serving the app listener. Use the accompanying error to diagnose the cause.
The destination agent's relay dial can also fail with
`application relay admission is unavailable` when the app listener is not
configured. Check that Wendy Net and app relay admission started on the
destination.

Cloud relay sessions last at most one hour. When Cloud closes an expired
TCP stream, the app opens a new connection to the same hostname and
published port. Wendy Net selects a route again for that connection and
opens a fresh relay if Cloud is still needed.

The app connects through its device's relay grant. The `wendy cloud tunnel`
command opens an operator session with separate permissions.

## Try the complete Python example

[Download the publisher and client](/media/mesh-mdns.zip), or use
[`Examples/MeshMDNS`](https://github.com/wendylabsinc/WendyOS/tree/main/Examples/MeshMDNS).
Both directories include a Dockerfile, pinned `zeroconf` dependency, and app configuration.
The publisher starts an HTTP server; the client discovers it and checks the response.

The publisher registers these records through `python-zeroconf`:

```python
info = ServiceInfo(
    "_http._tcp.local.",
    f"{instance}._http._tcp.local.",
    addresses=[socket.inet_aton(address)],
    port=8080,
    properties={"demo": "learn-mesh", "path": "/"},
    server=f"{hostname}.local.",
)
zc.register_service(info, allow_name_change=True)
```

This is the core excerpt; the download includes imports, server startup, interface
selection, and cleanup. `address` is the app's private `eth0` IPv4 address. The
process stays alive to advertise, and unregisters the service on shutdown.

The client uses `ServiceBrowser` for discovery. Its callback queues events; the main
thread resolves them and makes bounded HTTP requests. Use the returned address and
port, which can differ from those in the original announcement:

```python
info = zc.get_service_info(service_type, name, timeout=2000)
if info and info.properties.get(b"demo") == b"learn-mesh":
    addresses = info.parsed_addresses(IPVersion.V4Only)
    if addresses:
        url = f"http://{addresses[0]}:{info.port}/"
```

After unzipping, set the two device hostnames or IP addresses from `wendy discover`.
Replace both example values with your connected devices, then run:

```sh
PUBLISHER_DEVICE='publisher-device.local'
CLIENT_DEVICE='client-device.local'
cd mesh-mdns/publisher
wendy run --device "$PUBLISHER_DEVICE" --detach
cd ../client
wendy run --device "$CLIENT_DEVICE"
```

The explicit selectors keep both apps on their intended devices, even if
`WENDY_DEVICE` is set. Expect a resolved `10.99.x.x:18080` endpoint and JSON with `instance` and
`status: "ok"`. The client exits after success or a 60-second discovery timeout.
Its manifest sets `restartPolicy: "no"` so it stays stopped after exiting.
To check recovery, run `wendy run --device "$PUBLISHER_DEVICE" --detach` again
from `publisher/`, then rerun the client from `client/`. When finished, stop the
publisher:

```sh
wendy --device "$PUBLISHER_DEVICE" device apps stop com.example.learn-mdns-publisher
```

No Avahi entitlement or UDP 5353 mapping is needed for this app-owned socket.
The TXT marker filters demo instances; it is not authentication. See the
[python-zeroconf API](https://python-zeroconf.readthedocs.io/en/latest/api.html)
for integration into an existing application.

## Alternative: use private Avahi through D-Bus

Use this when your app expects Avahi's D-Bus API or a compatible `dns_sd.h` client
library instead of opening its own discovery socket. Add the following to the
same app's entitlement list, alongside its Wendy Net network entitlement:

```json
{ "type": "avahi" }
```

Install the Avahi client libraries your app uses in its container image. The agent
starts a private Avahi service for the app and supplies `DBUS_SYSTEM_BUS_ADDRESS`.
Use that address; do not mount the host's D-Bus socket or start a system-wide
Avahi daemon yourself.

For a diagnostic app image containing `avahi-utils`, run these **inside the app**:

```sh
avahi-publish-service "My API" _http._tcp 8080 "path=/"
avahi-browse --resolve _http._tcp
```

The publisher runs until interrupted, so run browsing in another process. The
publish command only announces the service; your server must already listen on
8080. The client app also needs `avahi` if it browses through Avahi. An app-owned
mDNS client can browse the same services without it.

Private Avahi needs an isolated network and cannot be combined with host networking
or the Bluetooth entitlement in the same container. The current D-Bus proxy supports
root clients; an app that drops privileges must retain a root process for its
Avahi client. A failed private Avahi service can leave the app running without
discovery; inspect its logs and restart the app if needed.

After an agent restart, the agent rebuilds private discovery for apps that remain
running. Avahi clients must reconnect to the bus; restart the app if its client
cannot recover. A redeploy rejected during validation leaves the running app's
discovery intact. An accepted replacement prepares a new private service before
starting the new app.

For an ordinary isolated app that needs Avahi only on its own bridge, `network`
mode `bridge` plus `avahi` is also supported. Use mode `mesh` for cross-device
Wendy Net discovery and access.

## Services on the physical LAN

When Ethernet or ordinary Wi-Fi is enabled for Wendy Net, entitled apps can also
see eligible IPv4 services announced on those directly connected networks.
Enable `--ethernet` or `--infrastructure-wifi` in the device's
[Wendy Net settings](/docs/guides/wendy-net).
These are local-network advertisements, not authenticated Wendy Net publications,
and they are not relayed onward across the net.

Access is limited to the advertised endpoint and port; discovering one service
does not give an app unrestricted LAN access. Names are discovery labels rather
than authentication. Use the service's own authentication where it needs it.
Extra endpoints encoded only in TXT do not receive LAN access grants. Protocols
that require them need separate eligible service advertisements or a deployment
where the peer participates as a Wendy Net app with all required ports published.

## Choose the right grants

| App needs | Configuration |
| --- | --- |
| Browse Wendy Net services with its own mDNS socket | `network` mode `mesh`, `serviceCIDR`, and isolated networking. |
| Publish an incoming Wendy Net service | The same, plus a matching TCP or UDP port mapping and a live app announcement. |
| Use Avahi or `dns_sd.h` client APIs | Add `avahi` and the client libraries in the image. |
| Make outbound Internet requests | `network` mode `bridge`; device roaming is configured separately. |
| Manage Wi-Fi Aware connections itself | Direct `nan` access, usually with host networking; this is a separate radio-control workflow. |

Neither `http` nor `avahi` alone grants Wendy Net access. Ordinary Wendy Net apps
do not need the administrative `admin` entitlement or direct Bluetooth/NAN access.
For multi-service apps, keep Wendy Net services in isolated networking and declare
the applicable entitlements per service. Shared host networking is a different mode.

## Troubleshoot discovery

1. Check `wendy net status` and `topology` on both devices.
2. Confirm both apps run with the intended private network and `serviceCIDR`.
3. Check the publisher listens on the container port and advertises its own IPv4
   address, a complete service record, and the matching transport type.
4. Check the declared port mapping. Publishing TCP does not authorize UDP.
5. If using Avahi, check the client library and supplied D-Bus address.
6. Resolve from the client app and test the returned endpoint, rather than an
   address copied from another device.

If only physical-LAN services are missing, check `wendy device logs`. Discovery
retries automatically after a temporary browser failure. If the log says LAN
projection was disabled because old access rules could not be removed, resolve
that cleanup error and restart the agent before trying again.

Stopping the publisher, withdrawing its announcement, or losing its route removes
the service after the relevant discovery and lease updates. After a partition or
restart, allow routes and service state to reconcile. An old cached record may
remain briefly; applications should handle disappearance and failed connections.

See the [network and Avahi reference](/docs/reference/app-configuration#network)
for detailed limits.
