## Camera Access

Camera access is used for webcam streaming, computer vision, image capture, and ML inference pipelines. WendyOS keeps camera devices hidden from apps by default, so your project needs a camera entitlement before the app can open `/dev/video*`.

Add the entitlement from your project directory:

```bash
wendy project entitlements add camera
```

The older `video` entitlement is still accepted for compatibility, but new projects should use `camera`.

For complete examples, follow these tutorials:

- [Adjust a camera's exposure](/docs/guides/camera-exposure)
- [Read a robot camera with OpenCV](/docs/guides/tutorials/python/robot-camera-opencv)
- [Process raw camera frames](/docs/guides/tutorials/python/raw-camera-frames)

A live stream can still contain stale or poor-quality observations. Check capture timestamps, exposure, motion blur, and calibration at the resolution your app uses. The [sensor fidelity exercise](/docs/integrations/sensor-fidelity) helps compare ideal simulated input with hardware.

## Inspect Cameras on a Device

Use the device camera commands to see which cameras WendyOS can see:

```bash
wendy device camera list
```

The output includes a device ID, transport type (`usb`, `csi`, `ip`, or `ros2`), name, and — for local cameras — a path such as `/dev/video0`. Network cameras show their address, while ROS 2 cameras show their topic. Network cameras without a stored login are hidden, and the table ends with how many it hid; `--all` shows them with a Status of `needs login`. See [IP Cameras](#ip-cameras) to pair one. Use the ID with view commands:

```bash
wendy device camera view --id 0
```

To request a specific stream shape:

```bash
wendy device camera view --id 0 --width 1280 --height 720 --fps 30
```

If you want to pipe the encoded stream instead of opening a local preview window:

```bash
wendy device camera view --id 0 --stdout
```

A view that names no `--width`, `--height` or `--fps` joins the camera at
whatever it is already doing, and an episode capture whose campaign does name
stream parameters may restart the producer under it. The stream is ended rather
than spliced, because the replacement producer emits a new sequence parameter
set; `camera view` then rejoins the new stream by itself and prints one line
saying so. Naming stream parameters yourself makes the view a holder that no
campaign can take over.

For broad hardware inspection, filter the device capability list:

```bash
wendy device hardware list --category camera
```

## Share a camera opened by an app

Wendy viewers and snapshots share one capture stream. If an app opens the
camera directly, for example through the RealSense SDK, Wendy can reuse that
app's JPEG feed when the device reports that it is busy. The app keeps running
and retains the camera.

To support automatic sharing, the process holding the camera must serve
`GET /frame.jpg` on a TCP listener bound to the host's loopback or wildcard
address. Each successful response must include:

- `Content-Type: image/jpeg`
- `X-Captured-At-Unix-Ns`: the frame's capture time in Unix nanoseconds
- A complete JPEG no larger than 8 MiB or 4096×2160 pixels

Wendy accepts frames captured within the last two seconds and polls at up to
10 frames per second. Omit `--fps` when viewing an app-owned JPEG feed, since
Wendy cannot reconfigure its capture rate. Repeated capture timestamps do not
create new frames.
It checks only listeners belonging to the camera process, does not follow
redirects, and respects HTTP errors such as a locked feed. A process holding
multiple color cameras is ambiguous and is not selected automatically.
Depth and infrared nodes do not inherit the color feed. Private container
network namespaces and original raw frames are not supported by this JPEG
fallback.

## Open a camera from an app while Wendy is using it

A V4L2 camera streams to one process at a time. While Wendy is capturing from a
camera, an app that opens the same `/dev/videoN` itself fails with
`Device or resource busy`. Wendy captures from a camera while:

- a `wendy device camera view`, a snapshot or another Wendy viewer is open on it
- a Wendy Data campaign that records it is armed or recording

To give the camera back to the app, close the view, or switch the campaign off
with `wendy data campaign disarm <campaign>`. `wendy data campaign arm <campaign>`
switches it back on.

Starting an app does not make Wendy open a camera. An app deployed with the
`camera` entitlement reads its own node at the camera's path, and Wendy
captures the camera only while an app reads its node (see the next section).

## Several apps on one camera

Every app you deploy with the `camera` entitlement gets its own agent-fed
device node at the camera's usual path, so several apps, live views and
recordings can read one USB camera at the same time. Add `"mode": "direct"` to
the camera entitlement to get the real device instead.

An app deployed before this version must be deployed again to get a camera
node. The extra device path that carried the H.264 of a camera that produces
it is gone: the app reads the camera at its own path.

Sharing covers local USB cameras that produce MJPEG, H.264 or packed raw
formats. These keep today's behavior and are not shared: CSI cameras, depth,
infrared and thermal streams, metadata nodes, SensorLink, ROS 2 and network
cameras. A device without a compatible
`v4l2loopback` module also gives the app the real camera.

### What an app gets

The app opens the same path as before, for example `/dev/video0` or its
`/dev/v4l/by-id` link, and sees one mode: one size up to 1280x720, one frame
rate, and YUYV when the camera itself produces MJPEG or H.264. `wendy run` prints one
line when this applies, naming each camera and its mode:

```
Camera: this app shares Brio 101 (video0) at 1280x720 YUYV, 30 fps. For the real device (its own formats, sizes and controls), set "mode": "direct" on the camera entitlement.
```

The line is not printed for `"mode": "direct"`, for apps without a camera
entitlement, for compose projects, or when the agent reports no shared mode
(an older agent, or no shareable camera).

When the app is deployed, it gets a node for every shared camera plugged in at
that moment, not only for the one it opens, so each of those cameras counts as
shared by the app (see below).

### Choose what the node carries

Two optional keys on the camera entitlement set what the node carries:

- `format`: `"pixels"` (default) for decoded pictures, `"native"` for the
  camera's own frames, for example MJPEG or H.264, or `"h264"` for H.264 with
  one whole frame per buffer.
- `stamp`: `"time"` (default) makes each frame's timestamp its capture time;
  `"frame"` puts the agent's frame number in the timestamp field instead, as
  `tv_sec * 1000000 + tv_usec`. That number is the frame's `sample_id` in a
  Wendy Data episode, so an app can match a frame it read to the frame the
  episode recorded.

On a camera that produces H.264, `"native"` and `"h264"` are the same thing:
the camera's own H.264, one whole frame per buffer. `"pixels"` on such a
camera are pictures decoded from it.

```json
{ "type": "camera", "format": "pixels", "stamp": "time" }
```

An app gets a node for every shared camera. A camera that cannot provide the
`format` asked for is served in another: pictures in place of `"native"` or
`"h264"`, and the camera's own frames in place of pictures that cannot be
made, for example from a camera that produces H.264 on a device without an
H.264 decoder. The deploy notice and the camera's status say
`asked for <format>; serving <format> because <reason>`. A compressed node's
largest frame is the image size the node reports; a larger frame is dropped.

A node keeps the format it was made with. When a camera stops providing it
while the app runs, for example because pictures can no longer be decoded from
its frames, the node's status is `cannot serve` with the reason, and deploying
the app again makes its node in a format the camera provides. While a picture
node is read, its status names the decoder: `pictures decoded by <element>`. A
`"frame"` stamp is never replaced by a time: a node whose camera's frames
carry no frame number gets no frames, and its status says why.

An app gets one node per camera. An entry's `allowlist` selects which cameras
its `format` and `stamp` apply to; an entry without one applies to every
camera. An allowlist entry names a camera by any identifier
`wendy device camera list --json` prints for it: its `stable_id`
(`by-id:usb-046d_HD_Pro_Webcam_C920-video-index0`, with or without the `by-id:`
prefix), its `path` (`/dev/video0`, or `v4l2:/dev/video0` as a campaign file
writes it) or its `name`. An entry cannot be empty.

Prefer a `by-id:` stable id: it follows the camera across reboots and
replugging. A `by-path:` stable id follows the port the camera is plugged into,
a device path can pass to another camera at a reboot or a replug, and a name is
shared by every camera of the model. Two cameras of one model without distinct
serial numbers cannot be told apart by stable id: name them by path, and expect
a replug to move the settings.

`wendy run` prints a line for each allowlist entry that selects no shared
camera's node, and for each that names a camera that is not shared through a
node, such as a network camera: such an entry configures nothing. An agent from
before stable id and `v4l2:` entries matches only the device path or the name,
and `wendy run` says so.

Two `camera` or `video` entries that claim the same camera must agree on
`format` and `stamp`. Validation compares allowlist entries as written, and
also knows `/dev/video0` and `v4l2:/dev/video0` for one camera, and a `by-id:`
stable id with and without its prefix. Entries that name one camera by
different identifiers, such as its stable id and its path, are only found on
the device: there the stable id decides before the path and the path before
the name, and `wendy run`, the agent's log and the camera's status say which
entry decided and which was passed over. Neither key can be used when any of
the app's camera entries has `"mode": "direct"`.

### Apps that need `"mode": "direct"`

Some apps cannot work with the shared mode:

- Apps that insist on MJPG, for example `ffmpeg -input_format mjpeg` or
  `v4l2src ! image/jpeg`. `HelloVLM` did, and was changed.
- Apps that ask for a size and do not read back what they got. `HelloVideo`
  did, and was changed.
- Apps that take a buffer's length and offset for `mmap` from the struct they
  passed to `VIDIOC_QBUF`, or map only buffer 0. The node fills in neither
  field on `VIDIOC_QBUF`, so `mmap` fails, and it hands out its buffers in turn.
  Map each buffer as `VIDIOC_QUERYBUF` describes it, and read the one
  `VIDIOC_DQBUF` returns. `HelloVideo` did both, and was changed.
- Apps that need more than 1280x720, a different frame rate, or camera
  controls.

`Examples/RemoteCam` works unchanged. For an app that breaks, either set
`"mode": "direct"` on its camera entitlement, or change it to accept the shared
mode.

```json
{ "type": "camera", "mode": "direct" }
```

### Viewers and recordings

A camera is shared while any app holds a node for it, and an app holds one for
every shared camera that was plugged in when it was deployed. That includes a
stopped app: its nodes stay until the app is removed. So while any such app
exists, even a stopped one, every camera it holds a node for runs only at its
shared mode, including cameras the app never opens.

While a camera is shared:

- A viewer or recording that names no size or rate joins the shared mode.
- One that names another size or rate is refused with a message naming the
  shared mode.
- A viewer already running at another mode is ended when an app starts reading.
- A recording at other parameters is not interrupted. The app's node gets
  frames once the recording leaves.

### Status of shared cameras

The Status column of `wendy device camera list` shows
`shared: <app> [format <format>, stamp <stamp>] (<state>), ...` for each app
sharing the camera. When the camera cannot fill a node in its format or with
its stamp, the state is `cannot serve` with the reason; the node gets no frames
until the camera can, which the agent checks once a minute. The same detail is
in the JSON from `wendy device hardware list --category camera --json` as the
properties `share_mode`, `share_unavailable`, `shared_with` and `share_state`,
with `share_mode_native` and `share_mode_h264` for the mode of a node in those
formats, or `share_unavailable_native` and `share_unavailable_h264` for why the
camera has none. A camera that is not shared carries `share_unavailable` with
the reason. Each camera's row also carries `stable_id`, the stable id
`wendy device camera list --json` prints for it and the one an allowlist entry
may hold; it is empty for a camera without one. A network or ROS 2 camera's
row carries `stable_id` and none of the share properties: an app reads it at
its own node, not through a share node.

### Behavior to know about

- **The camera is off while nobody reads.** No frames are captured, and no
  H.264 encoder runs while only apps read.
- **Apps deployed before the agent update are untouched** until you redeploy
  them. A camera plugged in after a deploy is shared only from the next deploy.
- **Each capture waits for a new camera frame.** Apps that open, read one
  picture and close receive a real frame, including after an earlier reader
  stops. The node does not return a black placeholder or replay the previous
  session's picture. If the camera is unavailable, capture waits for frames.
  Sharing requires the Wendy v4l2loopback module with `fresh_start` support.
  On older modules, sharing is unavailable and apps use the real camera
  directly, with its usual exclusive-access limit.
- **The frame rate is the camera's.** The node declares the camera's highest
  advertised rate, but the camera may deliver fewer frames: in low light, auto
  exposure lengthens each frame (a Brio 101 in a dark room gave 15 fps instead
  of 30). The Status column still says `reading` then.
- **An app with `"mode": "direct"` that holds the camera stops sharing.** While
  it has the camera open, sharing apps get no frames, and their Status says
  `no frames: the real camera is held by another app ("mode": "direct") or
  process`. The agent tries the camera again every 10 seconds, so frames
  return within about 10 seconds of the direct app letting go.
- **Replugging a camera.** The agent re-places each app's node about 2 to 3
  milliseconds after the camera reappears. An app that retries `open()` very
  fast can take the real camera for that moment, and then is not sharing until
  it reopens it. The agent logs this and shows it in the Status column.
- **Other apps' nodes are visible.** Their nodes appear at `/dev/video200` to
  `/dev/video255` and announce both capture and output. Open the camera's path
  rather than scanning for nodes.
- **Agent restarts.** An app that is already reading pauses for about a second,
  while the agent starts again and restarts the camera, and continues without
  reopening. An app that opens its
  camera while the agent restarts can open it and set its format, and gets
  frames once the agent is back. To make this possible, share nodes always
  announce both capture and output rather than capture only. Some readers, such
  as browser and WebRTC stacks, may reject that; this has not been tested.

## Wendy Lite cameras

Select a Wendy Lite board in the device picker, or use one saved as your default,
to list and view its SensorLink video channels directly:

```sh
wendy device camera list
wendy device camera view
wendy device camera view --id 4 --stdout > camera.mjpeg
```

Use a channel ID from `camera list`. A single video channel is selected automatically;
multiple channels open a picker. With `--non-interactive`, pass `--id` when several
channels match. Audio and other sensor channels are excluded.

The connection uses the board's existing USB, LAN, or BLE provider and its normal
credentials. The firmware must support SensorLink over WendyCom, including the
manifest and chunked `SensorData` messages.

The viewer supports MJPEG and H.264. `--stdout` writes the channel's encoded bytes
without transcoding, so use the codec shown by `camera list` when saving or piping
video. `--width`, `--height`, and `--fps` select an advertised channel with that
format; they cannot reconfigure or resize a stream. `--stable-id` and `--raw` are
unavailable for Lite cameras.

`camera list --refresh` fetches a fresh manifest. Its `--json` output is an array
of video descriptors with `channel_id`, `input_id`, `name`, and `video` format fields.
Channels sharing an `input_id` are alternative modes of the same input.

## ROS 2 Camera Topics

The WendyOS agent automatically presents ROS 2 video publishers as ordinary
cameras. It recognizes `sensor_msgs/msg/Image` and JPEG-encoded
`sensor_msgs/msg/CompressedImage`, allocates each topic a stable ID from
`128`–`199`, and feeds a matching `/dev/video<ID>` v4l2loopback device. The
topic then works with the same commands as a USB camera:

```bash
wendy device camera list
wendy device camera view --id 128
```

App-local ROS 2 graphs stay app-local. The agent creates its DDS reader inside
the running app's network namespace instead of changing the app's discovery
scope. Host/robot feeds on domain 0 are discovered on wired interfaces.

<Callout type="warning">
  DDS discovery on host-facing wired interfaces is unauthenticated. WendyOS
  treats peers on those robot networks as trusted: any peer publishing a
  supported image topic on domain 0 can appear as a camera. Keep untrusted
  devices on a separate network segment.
</Callout>

Unitree Go2 robots receive special handling: the native
`unitree_go/msg/Go2FrontVideoData` publisher on `/frontvideostream` appears as
**Unitree Go2 front camera**. Wendy accepts both the SDK-declared JPEG fields
and the resolution-tagged Annex-B H.264 layout emitted by current Go2 firmware,
preserving either codec through the loopback rather than transcoding it.

ROS 2 camera mirroring requires v4l2loopback 0.15.x's dynamic control API; the
WendyOS recipe is pinned to 0.15.4. Ubuntu 22.04's packaged 0.12.7 DKMS module
is not compatible even if it loads successfully. If a compatible module is
installed or loaded after an initial failure, retry the camera command; the
agent rechecks availability without requiring a restart.

The loopback uses exclusive capabilities. A container process that opens its
device immediately at startup may briefly find it output-only while the first
ROS 2 frame configures the capture format. Retry the initial format/open step
for up to the agent's 15-second first-frame window.

## IP Cameras

WendyOS also manages network (RTSP/ONVIF) cameras alongside local USB and CSI ones. A discovered camera is registered by its MAC address — the one identity that survives a DHCP address change — and given a device ID from a reserved band, `200`–`255`.

Discovery finds every ONVIF camera on the networks the device is connected to, including other people's cameras on a shared home or office LAN. So a network camera is used only once you store a login for it, which pairs it. Until then it is hidden from `camera list`, apps, and other clients, and WendyOS sends it nothing beyond the periodic discovery probe. A paired camera's ID never changes, even if its address does. An unpaired camera's ID can change when the agent restarts.

### Connect a camera directly to Ethernet

If a camera is plugged into a dedicated Ethernet port, WendyOS can give it a
network address. Leave this disabled on a shared LAN or the device's internet
uplink, where another DHCP server normally assigns addresses.

1. Find the dedicated port:

   ```sh
   wendy device camera dhcp status
   ```

2. Enable camera addressing on that port, replacing `eth1` with its name:

   ```sh
   wendy device camera dhcp enable eth1
   wendy device camera dhcp status
   ```

3. Wait for `serving`, then pair the camera in the **IP Cameras** tab of
   `wendy device pair`, or find its ID with
   `wendy device camera list --refresh --all` and store its login as described
   under [Credentials](#credentials).

`waiting` means the port is not ready yet. `blocked` or `degraded` includes a
reason, such as a competing DHCP server or an address conflict. The agent checks
the link periodically and stops serving if it detects an uplink or another server.
Enabling a port alone does not mean a camera is connected.

To disable it:

```sh
wendy device camera dhcp disable eth1
```

Settings and unexpired address reservations survive restarts and OS updates.
If you rename the interface, enable its new name explicitly. Add `--device`
to select a WendyOS device and `--json` for scripting.

#### DHCP status for scripts

`wendy device camera dhcp status --json` returns an `interfaces` array:

| Field | Meaning |
| --- | --- |
| `interface_name` | Port name. |
| `enabled` | Saved permission to assign camera addresses. |
| `serving` | The address server is currently active. |
| `present`, `carrier`, `up` | Port exists, has a link, and is enabled by the OS. |
| `ipv4_addresses` | Current addresses in CIDR notation. |
| `state`, `detail` | Current status and an explanation. |

Top-level `configuration_error` and `interface_error` describe failures reading
saved settings or inspecting ports. Missing false booleans and empty arrays may
be omitted; do not treat an inspection error as an empty port list.

### Discover and use the camera

Cameras are picked up automatically as the agent's periodic discovery runs. To force a discovery round immediately and list the results in one step:

```bash
wendy device camera list --refresh
```

Paired network cameras appear in the same `camera list` table as local ones, with `ip` in the Type column, the camera's address in the Where column, and a Status of `offline` or `ready`. The table ends with the number of cameras it hid for having no login. To pair one, use the **IP Cameras** tab of [`wendy device pair`](/docs/advanced/clients/wendy-cli/commands/device/pair), or find its ID with:

```bash
wendy device camera list --all
```

`--all` adds the unpaired cameras with a Status of `needs login`.

### Credentials

Most IP cameras require a login before they will stream, and storing one is also what pairs a camera. Store one with:

```bash
wendy device camera login <id>
```

This prompts for the password without echoing it, or reads it from the `WENDY_CAMERA_PASSWORD` environment variable when there is no terminal to prompt on (for example, in CI). The username defaults to `admin`; pass `--user` to override it. A camera that needs no login can be paired by pressing Enter at the password prompt. Credentials are stored on the device and are never returned by any command.

Remove a camera and its stored credentials with:

```bash
wendy device camera forget <id>
```

To validate a camera's stored login without starting a stream:

```bash
wendy device camera test <id>
```

`test` dials the camera's RTSP port directly and reports one of three outcomes: the credentials were accepted, the camera rejected them (with a `wendy device camera login <id>` hint), or the camera was unreachable. One nuance worth knowing: a camera that never actually challenged for a login — no authentication required, or just a bad stream path — is still reported as success, with a detail like *"did not request authentication; the stream path returned RTSP 404 and may be wrong"* rather than claiming the credentials were verified.

`wendy device camera view --id <id>` works the same way for network cameras as for local ones. If no credentials are stored yet, it reads `user`/`password` from a `camera` entitlement in `wendy.json` if present, or prompts once interactively, before retrying the stream — see the [`camera` entitlement fields](/docs/reference/app-configuration#camera) for the wendy.json-based option and its plaintext-storage caveat.

### Container Access

Apps with the `camera` entitlement (see [Camera Entitlement](/docs/device/entitlements#camera-entitlement)) see network cameras exactly like local ones: each paired camera is mirrored into a `/dev/video2xx` loopback node numbered to match its own device ID — camera `212` is always `/dev/video212` — and mounted into the container the same way USB and CSI devices are. Pairing a camera while such an app runs adds its node without restarting the app.

<Callout type="info">
  The loopback node always carries the camera's **sub-stream** — the same lower-resolution feed `camera view` chooses automatically for anything ≤1024px wide. There is currently no way for a container to request the camera's main/high-resolution stream instead.
</Callout>

<Callout type="warning">
  **Builds without the kernel module**: mirroring a camera into a container needs compatible v4l2loopback 0.15.x support. On a WendyOS build that lacks it (or in local development), the agent logs this once and moves on:

  > running build lacks compatible v4l2loopback 0.15.x support

  Direct IP-camera `wendy device camera view` and `camera test` are unaffected;
  only the in-container `/dev/video2xx` mirror is unavailable. ROS 2 cameras
  use a loopback node for both viewing and container access, so neither path is
  available until the compatible module is present.
</Callout>

## App Configuration

A minimal `wendy.json` camera app looks like this:

```json
{
  "appId": "com.example.camera",
  "platform": "linux",
  "version": "1.0.0",
  "entitlements": [
    { "type": "camera" }
  ]
}
```

To give one camera's node its own `format` and `stamp`, name the camera in the
entry's `allowlist`. The allowlist does not restrict which cameras the app can
open: it selects the cameras the entry's `format` and `stamp` apply to, and
the app still gets a node for every shared camera.

```json
{
  "type": "camera",
  "allowlist": ["by-id:usb-046d_HD_Pro_Webcam_C920-video-index0"],
  "format": "native"
}
```

## Camera identities in site models

Persist `stable_id` from the camera inventory when associating a camera with a
site marker. Pass that exact value to `StreamVideoRequest.stable_id` or
`wendy device camera view --stable-id <value>`. The agent resolves it when the
stream opens and rejects a missing identity instead of falling back to a reused
`/dev/videoN` number.

USB cameras use the existing `by-id:` or `by-path:` names. Paired SensorLink
cameras use `sensorlink:<pairing-key>:<channel-id>` and registered IP cameras use
`ip-mac:<mac>`. ROS cameras use `ros2:<key>`, scoped to their graph, domain and
topic so identical topic names in isolated apps stay distinct. A blank stable ID means the source cannot yet be saved safely as
a site camera. Marker placement is manual and does not calibrate the camera.

For paired MJPEG cameras, the agent delivers complete frames in order. Frames
that arrive together, such as after a brief network stall, are all delivered.
When a consumer falls behind, a pending frame that has waited too long is
replaced by the camera's next frame, so the consumer resumes at the newest
frame instead of replaying an older queue. Camera traffic does not evict queued
microphone or H.264 frames; those keep a bounded FIFO and can still drop
incoming frames when full. Recordings made from these live camera feeds can
therefore contain gaps under load. This delivery policy does not guarantee
capture of every source frame.

Native clients can discover enrolled SensorLink sources through the selected
gateway without a terminal UI:

```bash
wendy --device <gateway> --json device sensors list
wendy --device <gateway> --json device sensors add --source <principal_uri>
wendy --device <gateway> --json device sensors status
```

`add` chooses one exact enrolled principal from a new gateway-side discovery,
checks organization access, and lets the gateway verify the source certificate.
The returned pairing can have `connected: false`; saving a pairing is not proof
of arriving sensor data. These commands do not enroll a blank board or update
its firmware. CLI enrollment of a new Wendy Lite board requires USB; the native
macOS and iOS apps also offer Bluetooth setup on supported firmware.

For a USB-connected Wendy Lite board, use `wendy discover --json --type external
--timeout 5s`; the `usb` discovery filter alone scans WendyOS USB connections.
The external result includes the exact `wendy-lite:/dev/cu...` selector.
`wendy --device <selector> --json device enrollment-status` reads its hardware
ID, enrolled device UUID and tenant over USB without changing enrollment. Use
that UUID to match the source's gateway pairing instead of relying on its name.
A direct USB camera subscription can report `device busy` while a gateway owns
the source. In that case, view the gateway's shared feed.
