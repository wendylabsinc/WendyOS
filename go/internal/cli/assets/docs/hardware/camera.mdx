## Camera Access

Camera access is used for webcam streaming, computer vision, image capture, and ML inference pipelines. WendyOS keeps camera devices hidden from apps by default, so your project needs a camera entitlement before the app can open `/dev/video*`.

Add the entitlement from your project directory:

```bash
wendy project entitlements add camera
```

The older `video` entitlement is still accepted for compatibility, but new projects should use `camera`.

For complete examples, follow these tutorials:

- [Adjust a camera's exposure](/docs/guides/camera-exposure)
- [Read a robot camera with OpenCV](/docs/guides/tutorials/python/robot-camera-opencv)
- [Process raw camera frames](/docs/guides/tutorials/python/raw-camera-frames)

## Inspect Cameras on a Device

Use the device camera commands to see which cameras WendyOS can see:

```bash
wendy device camera list
```

The output includes a device ID, transport type (`usb`, `csi`, `ip`, or `ros2`), name, and — for local cameras — a path such as `/dev/video0`. Network cameras show their address, while ROS 2 cameras show their topic. Use the ID with view commands:

```bash
wendy device camera view --id 0
```

To request a specific stream shape:

```bash
wendy device camera view --id 0 --width 1280 --height 720 --fps 30
```

If you want to pipe the encoded stream instead of opening a local preview window:

```bash
wendy device camera view --id 0 --stdout
```

A view that names no `--width`, `--height` or `--fps` joins the camera at
whatever it is already doing, and an episode capture whose campaign does name
stream parameters may restart the producer under it. The stream is ended rather
than spliced, because the replacement producer emits a new sequence parameter
set; `camera view` then rejoins the new stream by itself and prints one line
saying so. Naming stream parameters yourself makes the view a holder that no
campaign can take over.

For broad hardware inspection, filter the device capability list:

```bash
wendy device hardware list --category camera
```

## Share a camera opened by an app

Wendy viewers and snapshots share one capture stream. If an app opens the
camera directly, for example through the RealSense SDK, Wendy can reuse that
app's JPEG feed when the device reports that it is busy. The app keeps running
and retains the camera.

To support automatic sharing, the process holding the camera must serve
`GET /frame.jpg` on a TCP listener bound to the host's loopback or wildcard
address. Each successful response must include:

- `Content-Type: image/jpeg`
- `X-Captured-At-Unix-Ns`: the frame's capture time in Unix nanoseconds
- A complete JPEG no larger than 8 MiB or 4096×2160 pixels

Wendy accepts frames captured within the last two seconds and polls at up to
10 frames per second. Omit `--fps` when viewing an app-owned JPEG feed, since
Wendy cannot reconfigure its capture rate. Repeated capture timestamps do not
create new frames.
It checks only listeners belonging to the camera process, does not follow
redirects, and respects HTTP errors such as a locked feed. A process holding
multiple color cameras is ambiguous and is not selected automatically.
Depth and infrared nodes do not inherit the color feed. Private container
network namespaces and original raw frames are not supported by this JPEG
fallback.

## Wendy Lite cameras

Select a Wendy Lite board in the device picker, or use one saved as your default,
to list and view its SensorLink video channels directly:

```sh
wendy device camera list
wendy device camera view
wendy device camera view --id 4 --stdout > camera.mjpeg
```

Use a channel ID from `camera list`. A single video channel is selected automatically;
multiple channels open a picker. With `--non-interactive`, pass `--id` when several
channels match. Audio and other sensor channels are excluded.

The connection uses the board's existing USB, LAN, or BLE provider and its normal
credentials. The firmware must support SensorLink over WendyCom, including the
manifest and chunked `SensorData` messages.

The viewer supports MJPEG and H.264. `--stdout` writes the channel's encoded bytes
without transcoding, so use the codec shown by `camera list` when saving or piping
video. `--width`, `--height`, and `--fps` select an advertised channel with that
format; they cannot reconfigure or resize a stream. `--stable-id` and `--raw` are
unavailable for Lite cameras.

`camera list --refresh` fetches a fresh manifest. Its `--json` output is an array
of video descriptors with `channel_id`, `input_id`, `name`, and `video` format fields.
Channels sharing an `input_id` are alternative modes of the same input.

## ROS 2 Camera Topics

The WendyOS agent automatically presents ROS 2 video publishers as ordinary
cameras. It recognizes `sensor_msgs/msg/Image` and JPEG-encoded
`sensor_msgs/msg/CompressedImage`, allocates each topic a stable ID from
`128`–`199`, and feeds a matching `/dev/video<ID>` v4l2loopback device. The
topic then works with the same commands as a USB camera:

```bash
wendy device camera list
wendy device camera view --id 128
```

App-local ROS 2 graphs stay app-local. The agent creates its DDS reader inside
the running app's network namespace instead of changing the app's discovery
scope. Host/robot feeds on domain 0 are discovered on wired interfaces.

<Callout type="warning">
  DDS discovery on host-facing wired interfaces is unauthenticated. WendyOS
  treats peers on those robot networks as trusted: any peer publishing a
  supported image topic on domain 0 can appear as a camera. Keep untrusted
  devices on a separate network segment.
</Callout>

Unitree Go2 robots receive special handling: the native
`unitree_go/msg/Go2FrontVideoData` publisher on `/frontvideostream` appears as
**Unitree Go2 front camera**. Wendy accepts both the SDK-declared JPEG fields
and the resolution-tagged Annex-B H.264 layout emitted by current Go2 firmware,
preserving either codec through the loopback rather than transcoding it.

ROS 2 camera mirroring requires v4l2loopback 0.15.x's dynamic control API; the
WendyOS recipe is pinned to 0.15.4. Ubuntu 22.04's packaged 0.12.7 DKMS module
is not compatible even if it loads successfully. If a compatible module is
installed or loaded after an initial failure, retry the camera command; the
agent rechecks availability without requiring a restart.

The loopback uses exclusive capabilities. A container process that opens its
device immediately at startup may briefly find it output-only while the first
ROS 2 frame configures the capture format. Retry the initial format/open step
for up to the agent's 15-second first-frame window.

## IP Cameras

WendyOS also manages network (RTSP/ONVIF) cameras alongside local USB and CSI ones. A discovered camera is registered by its MAC address — the one identity that survives a DHCP address change — and given a stable device ID from a reserved band, `200`–`255`. That ID never changes for the life of the camera, even if its address does.

### Connect a camera directly to Ethernet

If a camera is plugged into a dedicated Ethernet port, WendyOS can give it a
network address. Leave this disabled on a shared LAN or the device's internet
uplink, where another DHCP server normally assigns addresses.

1. Find the dedicated port:

   ```sh
   wendy device camera dhcp status
   ```

2. Enable camera addressing on that port, replacing `eth1` with its name:

   ```sh
   wendy device camera dhcp enable eth1
   wendy device camera dhcp status
   ```

3. Wait for `serving`, then discover the camera with
   `wendy device camera list --refresh`.

`waiting` means the port is not ready yet. `blocked` or `degraded` includes a
reason, such as a competing DHCP server or an address conflict. The agent checks
the link periodically and stops serving if it detects an uplink or another server.
Enabling a port alone does not mean a camera is connected.

To disable it:

```sh
wendy device camera dhcp disable eth1
```

Settings and unexpired address reservations survive restarts and OS updates.
If you rename the interface, enable its new name explicitly. Add `--device`
to select a WendyOS device and `--json` for scripting.

#### DHCP status for scripts

`wendy device camera dhcp status --json` returns an `interfaces` array:

| Field | Meaning |
| --- | --- |
| `interface_name` | Port name. |
| `enabled` | Saved permission to assign camera addresses. |
| `serving` | The address server is currently active. |
| `present`, `carrier`, `up` | Port exists, has a link, and is enabled by the OS. |
| `ipv4_addresses` | Current addresses in CIDR notation. |
| `state`, `detail` | Current status and an explanation. |

Top-level `configuration_error` and `interface_error` describe failures reading
saved settings or inspecting ports. Missing false booleans and empty arrays may
be omitted; do not treat an inspection error as an empty port list.

### Discover and use the camera

Cameras are picked up automatically as the agent's periodic discovery runs. To force a discovery round immediately and list the results in one step:

```bash
wendy device camera list --refresh
```

Network cameras appear in the same `camera list` table as local ones, with `ip` in the Type column, the camera's address in the Where column, and a Status of `needs login`, `offline`, or `ready`.

### Credentials

Most IP cameras require a login before they will stream. Store one with:

```bash
wendy device camera login <id>
```

This prompts for the password without echoing it, or reads it from the `WENDY_CAMERA_PASSWORD` environment variable when there is no terminal to prompt on (for example, in CI). The username defaults to `admin`; pass `--user` to override it. Credentials are stored on the device and are never returned by any command.

Remove a camera and its stored credentials with:

```bash
wendy device camera forget <id>
```

To validate a camera's stored login without starting a stream:

```bash
wendy device camera test <id>
```

`test` dials the camera's RTSP port directly and reports one of three outcomes: the credentials were accepted, the camera rejected them (with a `wendy device camera login <id>` hint), or the camera was unreachable. One nuance worth knowing: a camera that never actually challenged for a login — no authentication required, or just a bad stream path — is still reported as success, with a detail like *"did not request authentication; the stream path returned RTSP 404 and may be wrong"* rather than claiming the credentials were verified.

`wendy device camera view --id <id>` works the same way for network cameras as for local ones. If no credentials are stored yet, it reads `user`/`password` from a `camera` entitlement in `wendy.json` if present, or prompts once interactively, before retrying the stream — see the [`camera` entitlement fields](/docs/advanced/apps/wendy.json#camera) for the wendy.json-based option and its plaintext-storage caveat.

### Container Access

Apps with the `camera` entitlement (see [Camera Entitlement](/docs/device/entitlements#camera-entitlement)) see network cameras exactly like local ones: each registered camera is mirrored into a `/dev/video2xx` loopback node numbered to match its own device ID — camera `212` is always `/dev/video212` — and mounted into the container the same way USB and CSI devices are.

<Callout type="info">
  The loopback node always carries the camera's **sub-stream** — the same lower-resolution feed `camera view` chooses automatically for anything ≤1024px wide. There is currently no way for a container to request the camera's main/high-resolution stream instead.
</Callout>

<Callout type="warning">
  **Builds without the kernel module**: mirroring a camera into a container needs compatible v4l2loopback 0.15.x support. On a WendyOS build that lacks it (or in local development), the agent logs this once and moves on:

  > running build lacks compatible v4l2loopback 0.15.x support

  Direct IP-camera `wendy device camera view` and `camera test` are unaffected;
  only the in-container `/dev/video2xx` mirror is unavailable. ROS 2 cameras
  use a loopback node for both viewing and container access, so neither path is
  available until the compatible module is present.
</Callout>

## Thermal camera temperatures

A TOPDON TC001 in its stacked 512x484 mode carries a temperature for every
sensor pixel. The agent publishes them as live data streams, a grid and the
hottest and coldest pixel; see `wendy data stream` in the CLI reference.

Some TC001 units read every temperature about twice too hot, on any host, so a
room reads 45 °C and a hand 75 °C. Give such a camera its own correction:

```bash
wendy device camera thermal-calibration show
wendy device camera thermal-calibration set --id 4 --gain 0.48 --offset 0
wendy device camera thermal-calibration clear --id 4
```

The agent then publishes, for that camera only:

```text
corrected °C = gain × camera °C + offset
camera °C    = count / 16 - 273.15
```

It corrects the grid's `scale` and `offset`, the hottest and coldest markers,
and the check that a frame's mean is a plausible scene (-40 to 600 °C). Its
grids and markers carry the pair in a `correction` field, so a viewer can tell
corrected values from the camera's own. `gain` must lie between 0.1 and 10 and
`offset` between -100 and 100 °C; anything else is refused, as is a camera
without the TC001's stacked mode.

To measure the pair, clear any correction the camera has, then fill the frame
with ice water (0 °C) and then with boiling water, and read each with a
reference thermometer and with the camera. Take the camera's reading as the
median of a grid from `wendy data stream --stream
agent/camera/grid/v4l2:/dev/video4 --json`, not its hottest pixel, which is
one pixel's noise. Then:

```text
gain   = (t_hot - t_cold) / (r_hot - r_cold)
offset = t_cold - gain × r_cold
```

where `t` is the thermometer and `r` the camera. Water boils below 100 °C away
from sea level, so trust the thermometer. Check the result on a room and a
hand, which should read room temperature and 33 to 36 °C.

The line is the same as `celsiusCalibration` in wendy-console's Mac fire
detector, so a pair measured there works here. A Jetson edge-detector that
overrides its scale with `FIRE_THERMAL_COUNTS_PER_K=k` is the line
`gain = 16 / k`, `offset = 273.15 × (16 / k - 1)`.

The correction belongs to one camera: never copy it to another. The agent
keeps it by the camera's stable id (its `/dev/v4l/by-id` name), so it follows
the camera when a reboot renumbers `/dev/video*` or the camera moves to
another port, and the camera that takes its old number does not inherit it. A
camera without a stable id cannot be calibrated. Corrections are stored in
`/var/lib/wendy/thermal-calibration.json`, which on WendyOS lives on the data
partition, so they survive agent and OS updates. `clear --stable-id` removes
the correction of a camera that is no longer attached.

To get coloured areas on the video and an alarm without writing an app, for
example "40 to 50 °C yellow, above 50 °C red, alert on red", add `rules` to a
Wendy Data campaign. A rule reads the camera's grid on every frame, draws its
areas as live markers, and raises events that start a recording and send a
notification. Calibrate first: a rule's thresholds mean nothing on a camera
that reads double. See [rules](/docs/advanced/clients/wendy-cli/commands/data#rules)
in the data command reference.

## App Configuration

A minimal `wendy.json` camera app looks like this:

```json
{
  "appId": "com.example.camera",
  "platform": "linux",
  "version": "1.0.0",
  "entitlements": [
    { "type": "camera" }
  ]
}
```

To restrict the app to one camera device:

```json
{
  "type": "camera",
  "allowlist": ["/dev/video0"]
}
```

## Common Pairings

Camera apps often also need:

- `network` for HTTP or WebSocket video streams
- `gpu` for NVIDIA Jetson inference or accelerated image processing
- `persist` for saving snapshots or clips

For a camera plus GPU app:

```bash
wendy project entitlements add camera
wendy project entitlements add gpu
```

Then deploy:

```bash
wendy run
```
