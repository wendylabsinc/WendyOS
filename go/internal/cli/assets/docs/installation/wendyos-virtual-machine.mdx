New to Wendy? The [app tutorial](/docs/getting-started/app) deploys your first app to the simulator. This page explains what the simulator is and how to create and start one.

<Figure src="/images/get-started/simulator-lidar.webp" alt="A simulated Go2 robot standing between pallets in a warehouse scene, with lidar points drawn on the boxes around it" caption="A simulated Go2 in a custom warehouse scene, with its lidar returns drawn on the pallets." />

## What this is for

The simulator runs a real WendyOS ARM64 image on your own machine. It is the same
image a physical device runs — same agent, same containerd, same entitlements —
so you can build and deploy apps before you have hardware on your desk, or
alongside it.

On an Apple Silicon Mac this is also the fastest development loop WendyOS has.
`wendy run` targets `linux/arm64`, and an ARM64 guest on an ARM64 host builds
natively, with none of the emulation an x86 machine pays when it cross-builds
for a device.

<Callout type="info">
The VM exposes no physical camera, microphone, speaker, Bluetooth adapter, GPU or GPIO.
You can opt in to one physical serial port from the host through [managed serial passthrough](/docs/installation/simulator-management#serial-passthrough).
This is serial byte forwarding, not general USB passthrough. Unitree profiles publish simulated sensors over ROS 2.
Other physical peripheral access under **Hardware Access** needs a real device.
</Callout>

## What you'll need

QEMU, plus its ARM64 UEFI firmware:

<Tabs items={['macOS', 'Linux', 'Windows']} groupId="developer-machine-os" persist>
<Tab value="macOS">
```sh
brew install qemu
```
</Tab>
<Tab value="Linux">
On Debian or Ubuntu:

```sh
sudo apt install qemu-system-arm qemu-efi-aarch64
```

On Fedora:

```sh
sudo dnf install qemu-system-aarch64 edk2-aarch64
```
</Tab>
<Tab value="Windows">
```powershell
winget install --id SoftwareFreedomConservancy.QEMU --exact --source winget
```

Wendy finds QEMU in `%ProgramFiles%\qemu` even when it is absent from `PATH`.
The package includes ARM64 guest emulation and firmware for an x86_64 Windows
PC. `qemu-system-aarch64` names the guest architecture, not a host requirement.
</Tab>
</Tabs>

If QEMU or its firmware is missing, Wendy offers to install it through Homebrew
on macOS, WinGet on Windows, or apt-get or dnf on Linux. On Linux the install runs
`sudo`, so Wendy always asks first, even with `--yes`. Without an interactive
terminal, use `wendy vm start <name> --yes` to accept installation on macOS or
Windows, or run the package-manager command yourself.

QEMU and its firmware are the VM prerequisites. To build and deploy an app, you
also need a running container builder, such as Docker with Buildx. The image is
downloaded the first time you need one and reused for every virtual device afterward.

### Windows foreground VMs

Native Windows supports a generic VM for device inspection while its console
terminal stays open:

```powershell
wendy vm create dev --profile generic
wendy vm start dev
```

In another terminal, run `wendy --device vm:dev device info`, or select the
running VM in discovery. A stopped VM must be started in its own terminal.
The Simulator tab's create key displays these instructions and keeps discovery
open.

Local app builds for a VM, background VMs, managed robot simulators, and automatic
app-port forwarding require macOS or Linux. On Windows, run the Linux Wendy CLI,
QEMU, and your container builder inside WSL2 for the app tutorial's deployment
workflow. Native Windows still uses slower software emulation for the ARM64 guest,
so first boot can take several minutes.

## The short version

On macOS and Linux, you do not have to create or start anything by hand. With no `--device` and no
`WENDY_DEVICE` set, `wendy run` opens a picker with a **Simulator** tab:

```sh
wendy run
```

Pick a simulator and press enter. If it is stopped, it is booted for you. On a
fresh machine the first boot downloads the image, so it takes a few minutes.

The tab manages simulators without dropping to `wendy vm`:

| Key | Does |
| --- | --- |
| `c` | Create one at the latest release, naming it `sim`, `sim-2`, … |
| `s` | Start the highlighted VM and, the first time, build its robot |
| `x` | Power off the highlighted VM |
| `r` | Delete it and its disk, once it is stopped (asks first) |

On Windows, `c` in `wendy discover` displays the foreground VM commands and
keeps discovery open. Run those commands in a separate terminal.

`wendy discover` shows the same tab with the same keys. There `enter` copies
the VM's address instead of selecting it, and `s` returns to the tab once the
VM is up, rather than deploying to it. For a specific name, version or disk
size, use `wendy vm create`.

To skip the picker entirely, name the simulator directly:

```sh
wendy --device sim device info
```

`sim` starts the simulator if it is not already running. The rest of this page is the
manual equivalent, useful when you want several VMs or need to debug one.

## Simulate a Unitree robot

The `go2` and `g1` profiles add a virtual robot with MuJoCo, ROS 2, and a browser sandbox. Follow [Unitree simulator setup](/docs/installation/unitree-simulators), then [deploy a ROS 2 app from simulation to hardware](/docs/integrations/sim-to-real). Their virtual sensors do not provide access to physical peripherals.

## Simulate an SO-101 arm

The `so101` profile adds a virtual six-joint LeRobot SO-101 arm with MuJoCo and a browser viewer. It has no ROS 2 or DDS interface. Follow [SO-101 follower simulator](/docs/installation/so101-simulator).

## Create and start a VM

<Steps>
<Step>

### Create it

```sh
wendy vm create dev
```

The published image is downloaded and unpacked straight into the VM's disk. It
is cached compressed, so a second VM starts from the cache rather than the
network, and the raw multi-gigabyte image is never written twice. `--disk` sets
the disk size and WendyOS expands `/data` into the extra room on first boot; the
disk is sparse on supported filesystems, including NTFS on Windows, so the default
16 GiB VM does not allocate the entire capacity at creation. Before downloading, Wendy
prints the disk's path, virtual capacity, and available space on that volume.
Allow space for the decompressed image, the cached download, and later disk
growth. When the image's uncompressed size is known, Wendy checks that it fits
before writing. Container images live
on the root filesystem rather than `/data`, so a bigger disk does not give
`wendy run` more room.

To pin a version, or to run a VM from an image you built yourself:

```sh
wendy vm create dev --version 0.19.0
wendy vm create dev --image ./wendyos-image-vm-arm64-wendyos.rootfs.wic
```

</Step>
<Step>

### Start it

```sh
wendy vm start dev
```

This attaches you to the VM's console. Press **Ctrl-A** then **X** to power it
off.

</Step>
<Step>

### Talk to it

In another terminal:

```sh
wendy --device vm:dev device info
```

To avoid repeating it in this terminal:

```sh
export WENDY_DEVICE=vm:dev
wendy run
```

</Step>
</Steps>

## Troubleshooting

**`QEMU installation finished but qemu-system-aarch64.exe was not found on PATH or in %ProgramFiles%\qemu`.**
Check that `%ProgramFiles%\qemu\qemu-system-aarch64.exe` exists. If QEMU is
installed elsewhere, add that directory to `PATH` and open a new terminal.

**`no ARM64 UEFI firmware found`** — QEMU is installed but its firmware is not.
Run `wendy vm start` in a terminal to have Wendy offer the install, or install it
with the command under *What you'll need*. The error lists every path that was
searched.

**`host port already in use`** — something already holds 50051. Use `--port`.

**`shared networking needs macOS`** — `--net shared` builds on Apple's vmnet
framework. Use `--net user`.

**`socket_vmnet helper not found`** — `--net shared` needs the helper installed
*and* running. Install it as described in [Networking](/docs/installation/simulator-management#networking), or drop back to `--net user` and reach the
VM by address.

**`readiness probe timed out`, or the app's URL does not load.** The app's port
is not forwarded — see *Reaching an app you deployed*. The app itself is
usually running fine; check with `wendy vm logs <name>`.

**`Decompressor is not installed for grpc-encoding "gzip"`, then a registry
push that fails.** The agent in the VM's image is older than your CLI and cannot
accept compressed layers. The CLI falls back to a registry push and resolves
the selected VM's registry forward automatically, allocating another loopback
port if host port 5000 is busy. If the error reports an unavailable control
socket, restart the VM with the current CLI to enable forwarding. There is no
need to recreate its disk.

**It boots slowly.** On a Mac without Apple Silicon, or on an x86 PC, the guest
is emulated rather than accelerated, because the guest is ARM64 and the host is
not. It still works; it is just slower. `wendy vm start` prints which mode it
chose.
