---
name: device-control
description: Supervise local motion controllers and execute bounded goals on an identified device.
---

Inspect the exposed control API, device identity, fresh observations, and stop behavior before issuing a goal. Determine which local controller owns motion and avoid concurrent ownership. Preserve the user's requested scope and existing approval policy.

Keep actuator loops, command expiry, limits, and watchdogs in the local controller. Model response timing is not a real-time control loop. Express bounded goals with a completion condition and observe the controller's result before sending a conflicting goal.

Verify outcomes from fresh device evidence. Distinguish a command being accepted from motion completing. Report the goal, controller response, observed outcome, and any stop or incomplete state; do not imply that canceling chat undoes completed device actions.

For paired Go2 control, use unitree_pairings, robot_status, and robot_command. The interactive `wendy device pair --unitree` command is not a pairing-list API and must not run through workspace_exec. Use the selected digital twin controller for explicit natural-language movement requests. Start observations with robot_command action connect if needed; this does not require opening a map. "Turn around" means a bounded 180-degree turn. Use saved destination names for navigation; ask which destination when ambiguous. Never invent coordinates. Wendy manages command IDs internally; do not generate request_id. Retry uncertain commands with the same arguments and step. The optional step defaults to 1; increment it only for an intentional repeated identical command after the previous step completed. Only a completed controller result confirms completion. Report concrete controller blockers rather than inventing a requirement for a separate commissioned controller.

Before a requested movement, read robot_status and resolve any pending command receipt. When the requested move requires alignment and the robot is not aligned, announce one bounded robot_command action localize_active attempt as a prerequisite, without asking for a separate localization request. The movement request authorizes this prerequisite unless the user forbids extra motion. Do not localize again when already aligned or when the action does not need alignment. Follow the original localization receipt for at most five minutes, six turns and three nearby moves. Continue the original requested move in the same turn only after a completed receipt confirms Aligned=true. Refresh robot_find_object evidence after localization before go_to_object because the robot has moved. Do not resume after failure, cancellation or an unknown outcome, and do not repeat a failed search automatically. If alignment is lost between the status check and the requested move, report the terminal failure; never replay rejected movement using a new command identity. Plain align/localize, visual-only questions, and explicit no-motion requests do not authorize active localization. Keep obstacle, drop, measured-floor, freshness and emergency-stop guards. This prerequisite does not authorize expanded object search.

For a visual-only question such as "What does the Go2 see?", call robot_camera_snapshot immediately and describe the returned image briefly. It selects the single saved pairing itself; do not first inspect pairing, controller state, hardware, or ROS topics unless the snapshot reports a specific problem. This question does not authorize motion. For the Go2's onboard camera, use robot_camera_snapshot directly. camera_list lists cameras attached to the gateway and an empty list says nothing about the Go2 camera. For object queries such as "find the blue chair", use robot_find_object, which captures the Go2 camera and runs a local vision model. It does not move the robot. For "navigate to the door", first call robot_find_object with query="door", then call robot_command action go_to_object with the returned evidence_id if navigable=true. Complete both steps in the same turn when possible. Use the object description in the user's request as the query; never ask the user to provide an evidence ID. Use go_to only for a known saved destination. A visual-only question does not authorize approaching. If the result is non-navigable, explain its returned reason; if it identifies multiple possible objects, ask which one. Never invent an object distance or target from an image. If it is visible but cannot be ranged or routed, explain the concrete missing geometry. An ordinary object request such as "Find the blue chair" permits looking beyond the current view. First use robot_find_object. If a valid current-camera result has seen=false, announce and use robot_command action find_active with the same query, resolved robot and vision model. The bounded search uses live odometry and measured floor without a saved room, prior alignment or saved object location. Do not ask the user to reposition or separately request localization when this search is available. Honor earlier restrictions and explicit visual-only or no-motion requests; those stay stationary. A visible but non-navigable object is already found and does not need search movement. An explicit "walk around to find the door" can use find_active directly. A navigation request alone does not authorize expanded exploration. Follow the original search receipt, without restarting an incomplete or failed search. Active search stops when it sees a visual match or reaches its budget or a controller failure. A visual search result is not a navigable target; never approach using its bounding box. For "walk one meter forward", use action forward with distance_meters=1 (supported range 0.1–2m). Execute compound movement requests sequentially; stop the sequence if any part is not completed. Do not weaken obstacle/drop checks after a rejection.
