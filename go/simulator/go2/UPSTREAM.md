# Go2 runtime and robot asset provenance

The runtime uses the published `go2_moe_cts_164k_0.6715` locomotion policy,
the deployment parameters distributed beside its ONNX file, and the Go2 MJCF
and meshes from its author's MuJoCo deployment example. This bundle replaces
neither Unitree firmware nor its proprietary sport controller.

## Acquisition

From this directory, run:

```sh
python3 tools/fetch_assets.py
python3 tools/fetch_assets.py --check
```

The fetcher requires only Python 3.10+ and network access to GitHub's raw-file
host. Downloads go to `assets/` by default; `--output-dir` selects another
directory. `--check` is offline and exits nonzero for missing or altered files.
Each file has an immutable commit URL, byte length, and SHA-256 in
`assets.lock.json`. Valid files are reused. A failed or incorrect download
does not replace an existing file. Downloaded files are local build assets,
not source files to commit.

| [wty-yy/unitree_cpp_deploy](https://github.com/wty-yy/unitree_cpp_deploy/tree/a422ec4c5268b7922fecd40e74cbaea16ae3c8d9) | `a422ec4c5268b7922fecd40e74cbaea16ae3c8d9` | `go2_moe_cts_164k_0.6715` ONNX policy, its `deploy.yaml`, license |

The ONNX file lives upstream at
`logs/go2/go2_moe_cts_164k_0.6715/exported/policy.onnx`; it corresponds to the
`go2_moe_cts_high_slope_thre_164k_0.6715.pt` policy selected in the pinned
Python MuJoCo configuration. The author's [model collection](https://huggingface.co/wty-yy/go2_rl_gym_data)
identifies the 164k checkpoint as trained with self-collision enabled and
declares MIT licensing. The source repository's model and policy parameters
are retained together; a different Go2 model or checkpoint needs independent
validation.

## Runtime paths and exact policy contract

- `assets/policy/policy.onnx`: immutable CPU-inference policy.
- `assets/policy/deploy.yaml`: matching ONNX deployment parameters.
- `assets/policy/mujoco.yaml`: original Python simulation parameters for
  provenance. Its paths refer to the upstream checkout, its default scene is
  stairs, and its default forward command is 1 m/s; those are not local
  runtime launch settings. Wendy chooses the flat scene and starts stopped.
- `assets/robot/flat.xml`: original flat scene including `go2.xml`.
- `assets/robot/go2.xml` and `assets/robot/assets/*.obj`: matching robot body.
- `assets/licenses/`: notices copied into the downloadable runtime bundle.

The ONNX binary was inspected using ONNX and ONNX Runtime's CPU execution
provider. It has IR version 6, opset 11, and no external weight files:

| Tensor | Type and shape | Use |
| --- | --- | --- |
| Input `obs` | float32 `[1, 225]` | Five samples of each of the six terms below |
| Output `actions` | float32 `[1, 12]` | Raw joint-position offsets |
| Output `onnx::Unsqueeze_130` | float32 `[1, 8]` | Optional MoE weights |
| Output `onnx::Concat_159` | float32 `[1, 32]` | Optional latent representation |

Select `actions` by name; do not depend on autogenerated auxiliary-output
names. ONNX carries no hidden observation state; the runtime owns history.
The input is **term-major**: concatenate all five samples of angular velocity,
then all five samples of gravity, and so on. Samples within each term are
oldest first. Flattening five whole 45-element frames directly is incorrect;
the exporter performs that conversion internally. This is defined by the
pinned [ONNX exporter](https://github.com/wty-yy/go2_rl_gym/blob/30e74dc507bec7a642a8c98be26081f2c6f0822d/legged_gym/utils/exporter.py)
and [C++ observation manager](https://github.com/wty-yy/unitree_cpp_deploy/blob/a422ec4c5268b7922fecd40e74cbaea16ae3c8d9/deploy/include/isaaclab/manager/observation_manager.h).

| Term order | Values per sample | Scale after clipping |
| --- | --- | --- |
| Body angular velocity | 3, rad/s | `0.25` |
| Projected gravity | 3, body-frame unit gravity direction | `1` |
| Velocity command | 3, body `vx`, `vy`, yaw rate | `[2, 2, 0.25]` |
| Joint position minus default | 12, radians | `1` |
| Joint velocity | 12, rad/s | `0.05` |
| Previous raw policy action | 12 | `1` |

The paired configuration clips raw observations to `[-100, 100]` before
scaling. Its C++ history reset repeats the initial observation five times;
clear the previous action and recreate history on world reset. The Python
TorchScript artifact instead maintains its own zero-initialized history,
which is a distinct wrapper behavior, not permission to omit ONNX history.

Policy updates occur every 0.02 s and the original MuJoCo example uses
0.002 s physics steps. The output becomes
`q_target = default_joint_position + 0.25 * raw_action`, followed by PD torque
with `kp = 20` and `kd = 0.5` for every joint. The paired deployment config
clips raw actions to `[-100, 100]`; joint limits and force limits still apply.
The velocity ranges in the paired ONNX config are `vx [-2,2] m/s`,
`vy [-1,1] m/s`, and yaw rate `[-2,2] rad/s`; these are policy configuration
ranges, not a guarantee of tracking or terrain capability.

Joint and actuator order in this MJCF is `FL`, `FR`, `RL`, `RR`, with
hip/thigh/calf for each leg. Default positions in that order are:

```text
[0.1, 0.8, -1.5, -0.1, 0.8, -1.5,
 0.1, 1.0, -1.5, -0.1, 1.0, -1.5]
```

The SDK mapping `[3,4,5,0,1,2,9,10,11,6,7,8]` in `deploy.yaml` applies when
converting policy order to Unitree hardware motor slots. Do not apply it to
this model's already matching MuJoCo joint order. The body is named `base`,
the free joint is `root`, and the original base pose starts at z=0.445 m.
Hip/thigh force limits are +/-23.7 Nm; calf limits are +/-35.55 Nm. These
limits are on each joint's `actuatorfrcrange`, not the actuator `ctrlrange`.
The robot's default joint damping, armature, and friction loss are 0.001,
0.01, and 0.1 respectively. Retain those dynamics when adding a sandbox.

## Notices and changes

`licenses/go2_rl_gym.LICENSE` retains the author's MIT license and inherited
Unitree BSD-3-Clause notice. `licenses/unitree_cpp_deploy.LICENSE` retains
the author's MIT license and inherited Unitree Apache-2.0 notice. These are
unmodified files from the pinned revisions; their hashes also appear in the
asset lock. No separate per-mesh notice is present in the source robot
directory; retain the supplying repository's notices alongside those files.
Additional runtime packages have their own notices and are not covered by
these two files.

The acquisition process does not edit the upstream policy, model, meshes,
or parameters. Local sandbox construction and controller integration are
Wendy runtime code. Policy availability and CPU loading were verified;
walking, command behavior, and performance must be established by the
runtime's simulation tests and VM benchmark. No physical robot is involved
in asset acquisition or validation.

## Native Unitree ROS interfaces and SDK source

Fetch the unmodified native interface packages and a Python SDK checkout with:

```sh
python3 tools/fetch_unitree.py
python3 tools/fetch_unitree.py --check
```

This standard-library-only tool downloads two immutable source archives,
verifies their byte lengths and SHA-256 values, and extracts only manifest-listed
regular files. `unitree.lock.json` records both archives and all 305 extracted
file hashes. Files are replaced atomically after verification; symlinks, duplicate
archive members, and paths outside the output root are rejected. `--check` verifies
the archives and extracted files without network access. `--output-dir` selects
an alternative **project root**, rather than an assets directory.

| Source | Pinned commit | Local material |
| --- | --- | --- |
| [Unitree ROS 2](https://github.com/unitreerobotics/unitree_ros2/tree/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88) | `668d1ec5a05d1c38d3306bdca7d59f2ba3581a88` | Full `unitree_go` and `unitree_api` packages under `ros_ws/src/unitree/`, repository license |
| [Unitree SDK 2 Python](https://github.com/unitreerobotics/unitree_sdk2_python/tree/65691c8a8bc53b98d3976dba4dbf9d5d20b2e7f5) | `65691c8a8bc53b98d3976dba4dbf9d5d20b2e7f5` | Complete source checkout under `assets/sdk2_python/`, repository license |

The ROS archive SHA-256 is
`3e96da843c611878e28148ce113d978e5464dec922fc06dcd8c340f8232a6883`;
the SDK archive SHA-256 is
`b74e43fb6535929ec2a9efc1685e96111932ac6a9d7105b9cc7564ebaf6b7d58`.
Verified archives remain under `assets/archives/`. Retained BSD-3-Clause notices
are `licenses/unitree_ros2.LICENSE` and `licenses/unitree_sdk2_python.LICENSE`.
The fetcher neither installs nor imports the SDK and creates no DDS participants.
The pinned SDK declares `cyclonedds==0.10.2`, NumPy, and OpenCV Python as install
dependencies; downloading its source does not provide those runtime dependencies.

The complete ROS packages generate 24 `unitree_go` messages and eight
`unitree_api` messages, including their nested types and ROS introspection support.
Go2 does not require the separate `unitree_hg` package. The unmodified upstream
CMake files require `ament_cmake`, `geometry_msgs`, `rosidl_default_generators`,
and `rosidl_generator_dds_idl`. The last dependency is required by CMake but is
absent from the upstream `package.xml`; install
`ros-humble-rosidl-generator-dds-idl` explicitly in the ROS build container.
The stock `ros:humble-ros-base` image inspected here did not include it.
Use `colcon build --packages-select unitree_api unitree_go
--cmake-args -DBUILD_TESTING=OFF` from `ros_ws/` after sourcing ROS Humble and
installing the build dependencies. Both the adapter and ROS inspector processes
must source the resulting `install/setup.bash` overlay. A source hash check is
not evidence of a successful rosidl build or SDK interoperability.

**Pinned response signedness discrepancy:**
[`unitree_api/msg/Response.msg`](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/unitree_api/msg/Response.msg)
declares `int8[] binary`; the SDK's
[`Response_` IDL](https://github.com/unitreerobotics/unitree_sdk2_python/blob/65691c8a8bc53b98d3976dba4dbf9d5d20b2e7f5/unitree_sdk2py/idl/unitree_api/msg/dds_/_Response_.py)
declares `sequence[uint8]`. The fetched definitions remain unchanged. An isolated
test with these exact source versions received Request, Response, LowCmd, and
LowState through real ROS/SDK participants, but received **zero SportModeState
samples**: the SDK expects trailing `PathPoint[10] path_point` absent from ROS.

`tools/prepare_unitree.py` verifies all 37 pinned ROS input files before copying
them to `ros_ws/generated_unitree/`. This separate, authored compatibility overlay
appends `PathPoint[10] path_point` to `SportModeState.msg` and changes Response's
binary sequence to `uint8[]`. Every other input byte is preserved. The generated
`wendy-compatibility.json` records both source commits and every output hash.
`--check` verifies the inputs and exact derived output offline. The fetcher's
independent `--check` continues to validate the original sources and archives.

```sh
python3 tools/prepare_unitree.py
python3 tools/prepare_unitree.py --check
# From ros_ws, after sourcing ROS Humble:
colcon build --base-paths src/go2_command_ingress generated_unitree --cmake-args -DBUILD_TESTING=OFF
```

The runtime builds this overlay, not the stock packages. Trajectory following is
unsupported; all ten path points remain zero. These fields provide the SDK's
expected serialization layout, not synthetic trajectory feedback. The native
integration harness tests the unmodified SDK against this derived overlay and
separately tests whether a stock ROS reader accepts its trailing bytes. The
results apply to the tested ROS Humble/CycloneDDS pair, not all DDS vendors.

The pinned SDK Linux CRC constructor references native shared libraries absent
from its source archive. The test harness selects the SDK's existing portable
Python CRC branch during construction; it does not change message types, packing,
or the CRC algorithm. This accommodation is reported in acceptance output.
The harness installs the exact SDK with `--no-deps` plus `cyclonedds==0.10.2`;
OpenCV is unnecessary for these command/state checks. The old Python binding is
built against the ROS container's CycloneDDS library using a container-only
multiarch library-layout shim. See `integration/native/README.md` for commands.

The native sport service uses ROS `/api/sport/request` and
`/api/sport/response` (DDS `rt/api/sport/...`). Responses must echo both request
identity fields, `id` and `api_id`, with status code zero on success. The pinned
SDK's `Move` sends API 1008 with `{"x": vx, "y": vy, "z": yaw_rate}` and requests
no response; its return value reports local writer success, not command
acceptance. API 1 returns the raw version string `1.0.0.1`. Parameterless
`Damp` (1001), `StopMove` (1003), `StandUp` (1004), and `StandDown` (1005) expect
responses. The runtime implements those operations, BalanceStand (1002), and
read-only motion-switcher version/CheckMode requests. Stand-up/down use physical
joint transitions; walking uses the pinned policy. The stock low-level stand
example also calls unsupported motion-switcher mutations. The integration test
therefore explicitly grants a LowCmd publisher and tests its joint controller,
CRC, stop sentinels, and 40 ms watchdog separately. See `compatibility.json` for
the complete supported subset and `validation/native-sdk.json` for measured
SDK and stock ROS interoperability results.

## Render assets and virtual sensors

Physics always loads the original verified meshes. The default `balanced`
visual model shared by the browser and robot camera sensor uses meshes
generated with `fast-simplification==0.1.12` and `numpy==1.26.4`. `visuals.lock.json` records
every input/output hash and the generator hash. Generation runs on Linux ARM64
in the pinned container because floating-point simplification differs between
platforms; offline `--check` works on other hosts. Material boundaries and
60-degree normal creases are retained. A two-millimetre bounds guard keeps the
front lens mesh at full detail. Instanced visual triangles decrease from
398,432 to 120,417. Collision geometry, inertia, contacts and policy inputs
are unchanged. `GO2_VISUAL_DETAIL=full` selects the original visual meshes for
both browser and robot camera sensor rendering.

The browser sandbox receives that visual model's compiled geometry and
materials once from `/api/scene` (about 636 KB gzip at balanced detail). It
applies subsequent `/api/scene/state` body
poses locally, including obstacle changes and world resets. Its WebGL camera
supports orbit, pan and zoom. **Reset view** centers the current robot position
at the default viewing angle and distance. `/camera.jpg` remains a rendered
observation from the front camera sensor described below; sandbox viewing uses
the state endpoints.

Browser lidar overlays use the actual captured lidar returns. With ROS enabled,
the runtime retains the same sampled point cloud sent to `/utlidar/cloud` and
transforms it using its captured sensor pose. Without ROS, a shared on-demand
10 Hz sampler casts the same MuJoCo rays. `/api/scene/lidar` carries the capture
epoch, generation, time, origin and world-space points. Paused, disabled or
expired samples are omitted; seeded dropout applies to these observations.

The browser renderer vendors [Three.js r180 (0.180.0)](https://github.com/mrdoob/three.js/releases/tag/r180)
at immutable commit [`0af9729d0c143a86a1d725d6e2c3ad83301f3f34`](https://github.com/mrdoob/three.js/tree/0af9729d0c143a86a1d725d6e2c3ad83301f3f34).
The reviewed modules under `go2_sim/vendor/` are embedded in the CLI source
bundle and copied into both runtime images. All imports resolve to that same
runtime; no package installation, CDN or external browser request is needed.
The MIT notice is retained at `licenses/three.LICENSE`.

The ideal front camera is at `(0.40, 0, 0.04)` metres in `base_link`, looking
forward, with 60-degree vertical field of view and 640×360 RGB output. Its
optical frame follows ROS optical conventions. The runtime retains each MuJoCo
RGB exposure with its physics capture identity and wall timestamp. ROS publishes
those raw RGB bytes; `/camera.jpg` serves the same exposure encoded as JPEG.
Browser orbit, pan and follow controls affect only the sandbox viewpoint.
The virtual lidar is at
`(0.28, 0, 0.08)` metres and casts five simultaneous rings at elevations
−30, −15, 0, 15 and 30 degrees, with 360 azimuth samples per ring. `/scan`
uses the same horizontal ring and dropout mask as `/utlidar/cloud`.
These are documented virtual attachments, not measured factory calibration.

MuJoCo 3.3.7's batch-ray broad-phase bounds can omit valid intersections.
Lidar uses a private ray model with that broad phase disabled and copies the
captured geometry transforms; the physics model is untouched. Regression tests
compare every batch result against MuJoCo's scalar ray intersection across
random poses and obstacle placements. Images, IMU, contacts, lidar and joint
state retain the timestamps of the physics state that produced them; paused
or expired samples are not restamped as fresh observations.
