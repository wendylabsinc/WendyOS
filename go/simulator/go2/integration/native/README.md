# Isolated Unitree SDK acceptance

This harness exercises the pinned, unmodified Unitree Python SDK against the
Wendy Go2 simulator. Motion travels through real DDS/ROS messages. HTTP is used
for simulator identity, observations, explicit publisher grants, and reset.
The default local mode verifies that its Docker namespace contains only `lo`;
the motion harness verifies `simulation=true`, `robot=go2`, and
`profile_version=1` before importing the SDK or initializing DDS. The explicit
managed-VM mode below also verifies the VM name, enforced DDS isolation profile,
policy bundle, clock mode, and a runtime source pin.

From the repository's `go/` directory, with fetched assets available:

```sh
docker build -f simulator/go2/Dockerfile.ros -t wendy-go2-ros:dev simulator/go2
docker build -f simulator/go2/integration/native/Dockerfile -t wendy-go2-native-test:dev simulator/go2
docker run --rm --network none wendy-go2-native-test:dev python3 /app/native/type_pairs.py
docker run -d --rm --name wendy-go2-native-validation --network none -e GO2_NATIVE=1 -e GO2_RENDER=0 wendy-go2-ros:dev
docker run --rm --network container:wendy-go2-native-validation wendy-go2-native-test:dev
docker stop wendy-go2-native-validation
```

The simulator container has no external interface or published port. The test
container shares only that isolated namespace. `--output /results/native.json` can save the final JSON
when an explicit host output directory is mounted at `/results`.

## Prepare the deployed VM acceptance app

The VM app uses its guest's host network so it can reach the managed robot's
loopback DDS bus. It accepts only an explicitly named managed simulator whose
HTTP identity reports `dds_isolation: udp-rtps-loopback`. It pins the first
validated `source_digest` for all later reads and mutations, including the
separate ROS request worker. `--source-digest sha256:<hex>` can additionally
require a particular profile source pin from the outset. The SDK always
initializes domain 0 on interface `lo`; the ROS worker uses explicit loopback
discovery peers. The default isolated-container admission rules are unchanged.

From the repository's `go/` directory, after building the native dependency
image with the commands above:

```sh
python3 simulator/go2/integration/native/prepare_vm.py
docker build -f simulator/go2/integration/native/Dockerfile.vm -t wendy-go2-native-vm:dev simulator/go2/integration/native
docker run --rm --network none wendy-go2-native-vm:dev python3 /app/native/verify_vm_image.py
```

The exporter creates but never starts a temporary container, copies the pinned
SDK, compiled Cyclone bindings, exact ROS libraries and separately compiled
stock ROS messages, and removes the temporary container. Its ignored
`.vm-deps/manifest.json` records the source image and every exported file hash.
The initial ARM64 export is 90.5 MB from image
`67854778bec5e45959e8bb28402d72727da5d6256ad2cde1d240499cfd391699`.
It refuses to overwrite an existing export. Preserve or explicitly remove an
old export before rebuilding it against a different dependency image.

`Dockerfile.vm` uses `ros:humble-ros-base` and copied dependencies, so Wendy's
buildx OCI builder does not need to resolve a local Docker image in `FROM`.
It copies the current authored test files. The VM image contains no simulator
Python package or derived simulator ROS overlay. Its entrypoint sources only
stock ROS messages and the pinned SDK; offline validation checks those import
paths, loads the Cyclone RMW library, verifies SDK source hashes, and compiles
the client files without initializing DDS or contacting any VM.

Once the intended managed VM is ready and other motion tests have finished:

```sh
wendy --device vm:go2-sim run --prefix simulator/go2/integration/native --dockerfile Dockerfile.vm --build-type docker --builder docker --no-restart --user-args=--managed-vm,go2-sim --yes
```

This is a finite application (`sh.wendy.simulator.go2.integration.native`);
automatic restart must remain disabled. It resets and moves the virtual robot,
prints its complete JSON report, and releases command ownership on exit.
Preparing or offline-validating the image does not perform a VM deployment.

The harness consumes only existing HTTP diagnostics: `time`, `epoch`, `mode`,
`position`, `quaternion_wxyz`, `linear_velocity_world`, `ncontact`, `joints.q`,
`metrics.policy_updates`, and the `ros_commands` ownership/source registry.
The current production runtime preserves all of these fields. No internal
MuJoCo sampler/model object or simulator Python module is used by this app.

`type_pairs.py` sends synthetic fixtures on `/native_pair/*`, never command
topics. It tests both directions of the actual SDK interfaces, nonempty response
binary data, and a separately compiled stock ROS reader. The runtime uses the
explicit derivative generated by `tools/prepare_unitree.py`; the stock reader
uses the fetched unmodified ROS packages. The SDK is unchanged. The original
ROS SportModeState lacks the SDK's trailing ten path points and failed the
initial real DDS test; the derivative appends those fields with zero defaults.

`exercise.py` tests API version/correlation, source grants, signed walking and
StopMove, physical StandDown/StandUp, Damp and a fresh writer after reset,
unsupported/invalid/unauthorized ROS requests, no-response requests, LowState
20-slot layout and CRC, and external low-level PD standing. It checks CRC/mode
rejection and the 40 ms low-level watchdog, authority revocation, and absence of
automatic walking-policy resumption. Failed checks remain failures in final
JSON and cause a nonzero exit; no sample report is fabricated.

The pinned SDK's Linux CRC shared libraries are absent from its archive. The
harness selects the SDK's own existing Python CRC implementation during CRC
construction and reports that choice. It does not replace serialization or CRC
logic. CycloneDDS Python 0.10.2 is compiled against the image's ROS CycloneDDS
library, with container-only symlinks for its multiarch library directory. SDK
source/archive hashes are verified before installation; OpenCV is not installed.

The stock low-level stand example is not supported unmodified: it first calls
motion-switcher mutations that this profile deliberately returns as unsupported
(`3203`). CheckMode (`1001`) is read-only. Trajectory following and recovery are
also unsupported; path points are zero placeholders for wire compatibility.

The isolated run on 2026-09-12 passed all seven type-pair checks and all 13
command/state checks. Actual forward/backward displacements were +0.489 m and
-0.481 m. StandDown/StandUp changed base height from 0.076 m to 0.293 m; the
external low-level PD stand reached the same height with no policy updates.
The 40 ms watchdog was observed through HTTP after 41.0 ms. Runtime image:
`ba294c6a14f2c8f60ab8adfae03bd8db91ea87c4f33762eb18afbf61fd008a1f`;
test image: `67854778bec5e45959e8bb28402d72727da5d6256ad2cde1d240499cfd391699`.
The local report is `results/native/acceptance.json` (generated and ignored).
This validates local functional interoperability with rendering disabled; it
does not establish VM performance or physical-robot compatibility.
